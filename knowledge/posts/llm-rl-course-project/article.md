# LLM 强化学习大作业：从 20 行代码到 GRPO

如果一个刚开始学习 LLM 强化学习的学生只能做一个项目，我建议不要一上来复现一个超大模型的论文结果，而是做一个**可验证的小型数学问答训练器**：让一个小型指令模型回答简单算术题，程序自动判断答案，再用 GRPO 让模型逐渐更愿意生成正确答案。

这个项目有一个很好的学习特点：它既有明确的成功标准，又能把强化学习的每个环节暴露出来。你会亲眼看到一条完整闭环：

```text
模型生成回答 → 程序计算奖励 → 同题多回答形成组内优势
        → 策略损失 → 梯度更新 → 更新后的模型再次生成
```

最终交付物不是一个“跑出 loss 曲线”的脚本，而是一份能回答下面问题的实验报告：模型到底学到了什么？奖励是否可靠？GRPO 的哪一个环节真正改变了结果？

## 项目题目和任务边界

### 项目题目

**让一个小语言模型学会可靠地回答并解释小学算术题**。

第一版可以要求模型只输出最终整数，例如输入 `17 × 19`，输出 `323`。当这条最小链路跑通后，再增加“先给简短解释、最后用明确格式给答案”的要求。这样做是为了先把奖励和训练机制弄清楚，再处理自然语言解释带来的额外复杂性。

### 不做什么

- 不要求训练一个新的基础模型；从已有的小型 instruct 模型开始。
- 不把“训练奖励升高”当作成功；必须在未参与训练的测试题上评估。
- 不先使用一个黑盒 Trainer；先自己实现关键计算，再用 TRL 的 `GRPOTrainer` 做对照。
- 不把这个小项目的结果宣传成通用数学推理能力。它首先是一个理解训练闭环的实验。

## 为什么选这个项目

开放域聊天的奖励很难可靠定义：一句回答是否“有帮助”，常常需要人类判断或奖励模型。算术题则可以用程序精确判定，学生能够把错误定位到数据、答案解析器、奖励函数、采样还是优化器，而不是面对一条无法解释的曲线。

它也足够有趣。模型一开始可能输出带单位的句子、重复计算过程或格式不统一的答案；你可以观察它如何从“会生成文字”逐渐变成“更经常完成一个可验证任务”。稍后把算术判题器换成 Python 单元测试或 JSON Schema，仍然可以复用同一套框架。

## 大作业总览

建议把作业拆成 8 个里程碑。前两个里程碑不需要 GPU，第三到第五个可以用小模型和少量数据，第六到第八个负责把算法做成一个可信实验。

| 里程碑 | 要回答的问题 | 主要产物 |
| --- | --- | --- |
| 1. 20 行奖励函数 | 什么叫“答对”？ | 可测试的解析器和奖励函数 |
| 2. 生成与评分 | 模型生成的文本怎样变成样本？ | 一组 prompt、completion、reward |
| 3. 组内相对优势 | 为什么同一道题要采样多个答案？ | 手算并实现 GRPO 优势 |
| 4. 最小策略梯度 | 没有正确 token 标签，梯度从哪里来？ | 可运行的策略损失和更新 |
| 5. 稳定性 | 为什么更新不能走太远？ | 旧策略、裁剪或 KL 对照 |
| 6. TRL 复现 | 框架替你管理了哪些环节？ | `GRPOTrainer` 训练脚本 |
| 7. 独立评估 | 模型真的变好了吗？ | 基线、验证集、测试集和错误分析 |
| 8. 小型研究 | 哪个设计选择影响最大？ | 一个消融实验和最终报告 |

## 里程碑 1：20 行代码写出奖励函数

先不要加载模型。给定模型输出和标准答案，写一个函数：能提取最后一个整数，答对得 1 分，否则得 0 分。下面的代码只是任务骨架，学生可以改进它，但必须先为边界情况写测试。

```python
import re

def extract_integer(text):
    numbers = re.findall(r"[-+]?\d+", text)
    return int(numbers[-1]) if numbers else None

def reward(text, answer):
    predicted = extract_integer(text)
    return float(predicted == answer)

cases = [
    ("答案是 323。", 323, 1.0),
    ("17×19=322", 323, 0.0),
    ("我不会", 323, 0.0),
]

for text, answer, expected in cases:
    assert reward(text, answer) == expected
```

第一关的关键不是代码长度，而是让学生意识到：**奖励函数是训练目标的一部分**。如果解析器把题目中的数字当成答案，或者把“答案是 322，但正确答案是 323”解析错，后面的 GRPO 只会更努力地优化错误信号。

验收要求：补充至少 10 个测试样例，覆盖没有数字、多个数字、负数、带逗号和解释文字等情况，并说明哪些输出应该得到相同奖励。

## 里程碑 2：让模型生成并自动评分

准备包含 `prompt` 和 `answer` 的小数据集，并用一个已有的指令模型生成回答。先对每个 prompt 只采样几条回答，打印原文和奖励：

```text
prompt: 17 × 19 = ? 只输出最终整数。
completion: 17 × 19 = 323
reward: 1
```

这一步先不更新参数。学生要回答三个问题：

1. 模型是否确实在执行采样，而不是每次返回完全一样的答案？
2. 奖励函数给出的分数是否与人工判断一致？
3. 题目、标准答案和模型输出是否在同一个格式约定下？

训练数据至少分成 `train`、`validation` 和 `test` 三份。测试集不要只是训练题目的随机重复，可以改变数字范围、运算顺序或题目模板。

## 里程碑 3：手算并实现组内优势

GRPO 不只看一个回答得了多少绝对分，而是对同一个 prompt 生成一组回答，再比较它们在组内的相对好坏。给定奖励 `r₁, …, r_G`，先计算：

```text
Aᵢ = (rᵢ − mean(r)) / (std(r) + ε)
```

例如一题采样四个回答，奖励为 `[1, 0, 1, 0]`。两个答对的回答得到正优势，两个答错的回答得到负优势。若四个回答的奖励完全相同，组内没有可区分的方向，这一组提供的学习信号就很弱。

先用一个 Python 列表实现均值、标准差和优势，再用手算结果检查它。不要跳过这一步：很多“GRPO 代码能运行但不知道在做什么”的问题，都来自没有看过一个具体的奖励组。

## 里程碑 4：从优势得到最小策略梯度

强化学习不需要为每个位置提供一个人工正确 token。模型已经生成了一条回答，这条回答中的 token 被视为采取过的动作；奖励和优势只告诉我们这条路径值得鼓励还是抑制。

对采样到的 token，最小化下面的策略损失：

```text
L = − mean(Aᵢ · log πθ(tokenᵢ | prompt, prefixᵢ))
```

优势为正时，梯度倾向于提高这条回答的概率；优势为负时，梯度倾向于降低它的概率。这里的梯度来自模型 log-probability 对参数的导数，而不是奖励函数必须可导。

本关可以先用一个极小的字符级或词表级策略模型，不必直接对 0.5B 模型反向传播。要求学生打印一次更新前后的 token 概率，验证正优势样本的概率确实朝预期方向变化。

## 里程碑 5：加入旧策略与更新约束

如果对同一批样本无限制地重复更新，当前策略可能很快偏离生成这些样本的旧策略，训练会变得不稳定。因此加入一个旧策略快照，并比较新旧策略对已采样 token 的概率比：

```text
rᵢ(θ) = πθ(tokenᵢ | contextᵢ) / πold(tokenᵢ | contextᵢ)
```

可以实现一个最小的 clipped objective，或者比较加入 KL 惩罚前后的训练曲线。学生不需要在这一关复现所有工程优化，但必须画出策略偏移量、奖励和测试准确率，并解释“奖励升高但测试准确率下降”可能意味着什么。

## 里程碑 6：用 TRL 跑同一个任务

前面已经手工看过生成、奖励、优势和损失，才进入框架。使用 Hugging Face [TRL 的 `GRPOTrainer`](https://huggingface.co/docs/trl/main/en/grpo_trainer) 重写任务，最小接口类似：

```python
from datasets import Dataset
from trl import GRPOConfig, GRPOTrainer

train_data = Dataset.from_dict({
    "prompt": ["计算 17×19，只输出整数。"],
    "answer": ["323"],
})

def answer_reward(completions, answer, **kwargs):
    return [reward(text, int(gold))
            for text, gold in zip(completions, answer)]

config = GRPOConfig(
    output_dir="outputs/grpo-arithmetic",
    num_generations=4,
    max_completion_length=32,
    max_steps=50,
)

trainer = GRPOTrainer(
    model="Qwen/Qwen2.5-0.5B-Instruct",
    args=config,
    train_dataset=train_data,
    reward_funcs=answer_reward,
)
trainer.train()
```

实际提交不能只贴这段代码。需要记录 TRL 版本、模型版本、生成数量、最大长度、学习率、有效 batch size 和随机种子。还要说明当前框架实现与论文公式的差异，例如 KL 是否启用、奖励如何缩放，以及使用了哪种 loss 变体。

## 里程碑 7：建立可信的评估

至少报告以下指标：

- 训练前和训练后的测试题正确率；
- 训练集、验证集和测试集的格式通过率；
- 平均回答长度，以及回答是否越来越冗长；
- 组内奖励标准差和奖励全相同的比例；
- 20 个随机测试样例的原始输出与人工检查。

要特别检查奖励漏洞。例如奖励只取“最后一个整数”，模型可能输出一长串数字并把正确答案放在最后；格式奖励过强时，模型可能只学会输出固定模板。测试集应使用独立的答案计算和解析逻辑，不能把训练奖励函数原样当成唯一真相。

## 里程碑 8：完成一个小型消融实验

选择一个问题即可，不需要同时做很多实验。推荐二选一：

1. 只使用正确性奖励，对比“正确性 + 格式奖励”；
2. 固定其他设置，比较 `num_generations=2` 和 `num_generations=8`。

每个设置至少跑两个随机种子，报告均值和波动，并给出一段失败案例分析。报告不能只写“设置 A 更好”，还要解释它如何改变了奖励的可区分性、采样多样性或策略更新稳定性。

## 最终提交清单

最终项目可以按 Stanford CS234、Stanford CS224R 和 UC Berkeley CS285 公开课程中常见的“实现 + 分析 + 报告”方式组织，但内容是为 GRPO 重新设计的：

```text
project/
├── README.md                 # 如何安装、运行和复现实验
├── reward.py                 # 答案解析与奖励函数
├── rollout.py                # 生成、记录和评分
├── min_grpo.py               # 手写的最小优势与策略损失
├── train_trl.py              # TRL GRPOTrainer 版本
├── evaluate.py               # 独立验证与测试
├── tests/                    # 奖励、解析和数据划分测试
├── configs/                  # 模型、种子和训练配置
└── report.pdf                # 方法、曲线、消融和失败案例
```

报告至少回答：

1. 任务、奖励和数据划分是怎样定义的？
2. 一个回答如何从文本变成 reward，再变成 advantage 和 loss？
3. 手写实现与 TRL 实现的对应关系是什么？
4. 训练前后独立测试是否改善？有没有奖励投机？
5. 哪个消融结果最能说明你的结论？

## 从算术题继续扩展

当算术项目稳定后，可以只替换“可验证器”，保持 GRPO 主循环不变：

- **代码任务**：在沙箱中运行单元测试，以通过的测试比例作为奖励；
- **结构化输出**：用 JSON Schema 检查字段、类型和数值约束；
- **小游戏任务**：让模型选择动作，用游戏得分作为稀疏奖励；
- **工具调用**：检查调用参数是否满足 API 约束，并对最终结果评分。

每次扩展都要重新问：奖励是否可计算？是否会被模型投机？独立测试是否真的测量目标能力？这三个问题比更换一个 Trainer 名称更重要。

## 一句话验收标准

学生不只是“成功调用了 `GRPOTrainer`”，而是能够从 20 行奖励函数开始，独立解释并验证：**一组回答怎样得到奖励，奖励怎样形成相对优势，优势怎样改变策略概率，以及这种改变是否在独立测试题上带来了真实改善。**
