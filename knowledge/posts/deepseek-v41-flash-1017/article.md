# DeepSeek V4：训练全流程

> 本文以 [DeepSeek V4.1-Flash 官方资料](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017) 为切入口，重点解释一台现代大语言模型从数据到部署是怎样训练出来的。V4 的具体模块只作为范式中的例子；不把某个创新点写成整篇文章的主角。公开报告、教学解释和没有公开确认的细节会明确分开。

## 先建立一张总地图

一台可用的 LLM 不是“把一篇论文丢进 Transformer 就训练出来”。更准确的顺序是：

```text
数据与许可
  → 清洗、去重、混合与 tokenizer
  → 预训练：学习语言、代码和跨模态表示
  → 中期训练：补长上下文、领域和任务分布
  → 监督微调（SFT）：学习遵循指令
  → 奖励建模与强化学习（RL）：学习选择更好的回答
  → 蒸馏与安全对齐
  → 离线评测、红队测试和部署优化
```

每一阶段都有自己的输入和输出。前一阶段的输出通常是后一阶段的初始化，而不是每个阶段都从零训练一个新模型。训练顺序也有原因：先让模型获得稳定的通用能力，再要求它遵循指令、满足偏好；如果反过来直接做 RL，奖励模型很容易把“不会”误判成“会说得像”。

## 1. 数据：模型先要知道自己要学什么

### 输入

数据可能包括网页文本、书籍、代码、数学与科学文本、对话，以及图像和图像说明。多模态模型还需要把图像、文本等不同来源对齐到同一个训练流程中。DeepSeek V4 公开材料提到约 **45 T 多模态 token** 的训练规模；这里的 token 是把不同模态转成可计算序列后的统一计量，不等于 45 T 句子。

### 数据工程做什么

工程流程通常包括来源许可检查、语言与格式过滤、近重复和精确重复去除、质量打分、危险内容过滤、数据配比和 train / validation 切分。不同数据的权重也要控制：代码过多会损害普通语言能力，重复网页过多会让模型记忆训练语料而不是学习规律。

### 输出

这一阶段的输出不是模型，而是带版本号的数据清单、分片和采样权重。数据版本必须可追踪，否则后面发现评测退化时无法知道是哪次数据混合造成的。V4 的公开资料没有披露全部数据来源、过滤阈值和每一类的精确比例，因此下面只解释通用范式，不把未公开配方写成事实。

## 2. Tokenizer 与多模态输入

标准文本 LLM 使用 tokenizer 把字符串变为 token id。多模态模型还需要一个视觉编码器：图像先变为视觉特征，再投影为模型能够读取的视觉 token。这样，主干 Transformer 可以在同一序列中处理“图像 token + 文本 token”。

这一步的关键输出是三件东西：tokenizer 词表、视觉编码器及其投影、统一的输入格式。输入格式决定了训练和推理时的特殊 token、图像位置、工具调用标记等；格式不一致，即使权重正确，模型也可能表现异常。V4.1-Flash 的模型资料还特别说明没有可直接套用的通用 Jinja chat template，所以使用时应遵循官方 prompt encoding 方式，而不是猜一个模板。

## 3. 架构：为什么 V4 仍然是自回归模型

从读者熟悉的 Transformer 看，模型仍然进行 next-token prediction：给定前面的 token，预测下一个 token。V4 的变化主要是把“怎样处理输入、怎样存历史、怎样容纳更多参数”做得更适合大规模和长上下文任务。

### 3.1 CED：编码输入，解码输出

V4.1-Flash 资料公开了 Causal Encoder-Decoder（CED）路线。可以把它理解成两段 Transformer：编码器先把长输入压成可复用的表示，解码器再按自回归顺序生成答案。旧的 decoder-only 模型在 prefill 时处理完整提示词，生成时反复读取历史；CED 试图把“读取长输入”和“逐 token 写答案”分工，降低长输入的重复成本。

输入是提示词或多模态序列，编码器输出是上下文表示，解码器输出是每一步的 next-token logits。CED 不是把生成改成扩散，也不是一次性生成整段文本。

### 3.2 CSA2 与长上下文缓存

生成时模型要读取过去 token 的 Key / Value（KV）。若每个层、每个位置都完整保存，长上下文会同时带来显存和访存压力。Compressed Sparse Attention 2（CSA2）把历史分成近期局部信息和经过压缩、索引的全局信息：近期窗口保留细节，较远历史通过压缩表示和稀疏选择访问。不同层还可以采用 Full、Reindex、Reuse 等模式。

这解释了“KV cache 压缩”在系统中的位置：它不是训练目标本身，而是让推理阶段的历史状态更便宜。V4.1-Flash 资料报告了全局 KV 的压缩存储量级，但不同实现、精度和上下文长度会改变实际占用，不能直接把报告数字当作任何硬件上的固定显存。

### 3.3 MoE：总容量和单 token 计算分开

Mixture of Experts（MoE）把前馈网络拆成多个专家。路由器为每个 token 选择少数专家，因此模型可以有很大的总参数量，但每个 token 只激活其中一小部分。公开模型资料给出 V4.1-Flash 约 **552 B** 总参数，并报告每个 token 只激活约 **8 B**（prefill）或 **16 B**（decode）量级的参数；这不是说 552 B 模型可以放进一张 8 B 显存的卡，而是说单 token 的计算量低于总权重容量。

MoE 的输入是 token 表示，输出是被选专家的加权结果。训练时还要处理负载均衡、专家并行和跨设备通信。V4 资料没有公开所有路由损失、容量因子和并行切分细节，不能据此编造完整配方。

### 3.4 其他模块放在什么位置

V4 / V4.1-Flash 材料还提到滑动窗口重算、残差连接稳定化、Engram 条件记忆和推理草稿验证等设计。它们分别服务于局部缓存恢复、深层优化、知识访问和推理速度；理解端到端训练流程时，把它们看成架构或系统中的局部组件即可。它们不是替代预训练、SFT 和 RL 的另一套训练顺序。

## 4. 预训练：让模型获得通用能力

### 输入与目标

预训练输入是大规模 token 序列（文本、代码或多模态序列），目标通常是让模型最大化下一个 token 的概率，也就是最小化 next-token cross-entropy。没有人逐 token 提供“标准答案”；数据本身的后续 token 就构成了自监督目标。

### 一次训练步发生什么

1. 数据加载器取一批序列并切成 micro-batch。
2. 模型前向计算 logits，得到每个位置的预测。
3. 将 logits 与真实下一个 token 计算交叉熵。
4. 反向传播得到梯度，使用优化器更新参数。
5. 多卡之间同步梯度或参数分片，并保存 checkpoint、吞吐和 loss。

大模型通常同时使用数据并行、张量并行、流水线并行和 MoE 专家并行。优化器状态、梯度和激活也要分片；因此“总参数量”不能直接换算成“需要多少张卡”。

### 为什么还要中期训练

基础预训练结束后，模型可能会写通用文本，但长上下文、代码、工具调用或视觉任务未必稳定。中期训练（mid-training）用更集中、更高质量的数据继续训练，例如长文档、代码、跨模态交错数据或特定领域语料。它的输出仍是一个基础模型 checkpoint，而不是已经会聊天的助手。

公开资料没有给出 V4 每个阶段的完整 token 配比、学习率曲线和训练步数。本文只保留“预训练 → 中期训练”的职责划分，不猜测这些数字。

## 5. SFT：把基础模型变成会按要求回答的模型

SFT 的数据是指令、上下文和高质量示范答案，例如：

```text
用户：解释一个 Python 函数
助手：给出步骤、代码和检查方法
```

训练时仍然是交叉熵梯度更新，但损失通常只计算助手答案区域。也就是说，SFT 有相对明确的示范文本作为监督；它和预训练共享优化形式，却使用了不同的数据分布和目标区域。

SFT 的输入是 prompt / response 对，输出是更遵循指令的模型。数据还可能包含工具调用、拒答、安全规范和视觉问答。SFT 不是“把所有人的偏好都平均记住”，所以它之后通常还需要偏好优化或 RL。

## 6. RL、偏好优化与蒸馏：让回答更符合目标

### 6.1 奖励从哪里来

强化学习不需要每一步都有一个唯一正确 token，但需要对完整回答或中间过程给出可比较的反馈。反馈可以来自人工偏好模型、规则验证器、代码执行结果、工具环境状态或安全分类器。一个回答得到 reward 后，策略会提高产生高 reward 轨迹的概率，同时用 KL 约束避免偏离参考模型过远。

### 6.2 在线 RL 的基本回合

1. 当前策略接收 prompt，采样多个回答。
2. 奖励模型或环境评估这些回答。
3. 根据 reward 计算优势或组内相对分数。
4. 用 PPO、GRPO 等目标更新策略参数（通常只更新 LoRA 或策略模型的一部分）。
5. 在新的策略上再次采样，并检查奖励、通用能力和安全指标。

DeepSeek 的公开材料把后训练概括为 SFT、RL 和 on-policy distillation（OPD）等阶段；但不同版本的具体数据、奖励器、回合数和损失权重并未完整公开。教学上可以把 OPD 理解成：让当前策略在真实采样分布上学习更强教师或更可靠目标的输出，从而把策略优化后的能力压缩回可部署模型。

### 6.3 为什么不能只做 RL

如果奖励函数只奖励“回答很长”，模型可能学会废话；如果人物奖励只看口吻，模型可能编造事实。因此实际流程通常先用 SFT 建立可用行为，再用可验证奖励做小步 RL，并用独立评测集观察通用能力是否退化。

## 7. 评测与部署：训练结束不等于可以上线

评测至少包含通用知识、推理、代码、长上下文、多模态、工具调用、安全和延迟 / 成本。每次 checkpoint 都要记录数据版本、代码版本、配置、随机种子和硬件环境，否则指标无法复现。

部署阶段还要做权重格式转换、量化、张量 / 专家并行、KV cache 管理、批处理和服务限流。V4.1-Flash 的 Flash 取向主要体现在这些高效推理路径与模型规模 / 激活量的组合上，而不是把训练目标换成另一种模型。

## 8. 1017 版本只需要这样理解

DeepSeek-V4.1-Flash-1017 是 V4.1-Flash 的一次 **minor update**。官方模型卡主要展示推理、代码、智能体、视觉基准和任务执行效率的变化；没有完整披露新增数据、训练步数或损失函数，因此不能把某个分数提升归因到一个确定的新算法。阅读这篇文章时，把 1017 当作同一 V4 范式上的更新版本即可。

## 9. 如何使用与后训练这个模型

### 9.1 先做 LoRA-SFT

如果目标是增强模型对几个特定人物的能力，先定义是“记住事实”还是“稳定扮演风格”。事实类目标应准备有来源的问答和检索评测；风格类目标应准备多样、去重、经过人工检查的对话。先冻结主模型，只训练 LoRA 适配器，再在独立人物集和通用集上比较基线。

训练数据必须遵循官方 prompt encoding；不能因为模型看起来像聊天模型，就直接套用别的模型的 Jinja 模板。视觉输入、工具调用和思考模式也要保持一致。

### 9.2 再考虑 LoRA + RL

只有当目标可以被可靠地评分时才做 RL。例如：人物事实是否可由资料核验、回答是否保持角色设定、是否避免把不同人物混淆。一个小规模流程可以是：

```text
原模型基线
  → LoRA-SFT
  → 独立评测与奖励器校准
  → 多回答采样
  → GRPO / PPO 更新 LoRA
  → 通用能力、安全和人物集回归测试
```

### 9.3 粗略硬件估算

以下只是规划区间，不是官方实测。假设 LoRA rank 为 **16–32**，主模型权重冻结；每次输入约 **1 K**、输出最多 **512** token；约 **2,000** 个 prompt，每个 prompt 采样 **4** 个回答，做 **1–2** 轮；上下文控制在 **2 K** 以内；并且已经找到支持该模型 CED、MoE、CSA2 和官方编码格式的训练框架。实际还要加 rollout、奖励器、通信和失败重跑。

| GPU 类型 | 建议起步规模 | LoRA + 在线 RL 粗估耗时 | 说明 |
| --- | ---: | ---: | --- |
| RTX 4090（24 GB） | 32–64 张 | 很难给出可信小时数 | 显存和互联都是主要瓶颈，不建议作为首个平台 |
| A800（80 GB） | 16–32 张 | 约 48–220 小时 | 依赖量化训练内核、专家并行和高速互联 |
| A100（80 GB） | 16–32 张 | 约 48–200 小时 | 需要验证该模型的量化与训练实现 |
| H100（80 GB） | 16–32 张 | 约 24–120 小时 | FP8 和互联可能提高吞吐，但不能保证直接兼容 |
| H200（141 GB） | 8–16 张 | 约 18–96 小时 | 显存更宽裕，仍受 rollout 和框架影响 |
| B200（180 GB） | 8–16 张 | 约 12–72 小时 | 依赖相应 FP8 / FP4、专家并行和 RL 实现 |

552 B 参数按 BF16 裸权重约为 **1.10 TB**；按 8 bit 约 **552 GB**，按 4 bit 约 **276 GB**，这些数字还没有算激活、梯度、KV cache、通信缓冲和视觉模块。即使只训练 LoRA，冻结权重也必须参与前向；不能因为 decode 激活量约 **16 B** 就推断一张卡可以训练完整模型。

如果只有 **1–8 张 80 GB** 卡，更现实的顺序是先做 API / 推理基线、奖励设计和小模型验证，再做 4 bit LoRA-SFT 兼容性实验。只有小规模完整回合跑通并测得真实 token / s 后，才值得外推大规模 RL 时间。
