# DeepSeek V4.1 Flash：架构与后训练

> 本文讨论 [DeepSeek-V4.1-Flash-1017 官方模型](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017)。它是 V4.1-Flash 的一次小版本更新。下文把 **V4.1-Flash 技术报告中的架构**与 **1017 模型卡确认的更新**分开讲；后训练资源部分是工程估算，不是官方实测。

## 一句话认识这个模型

普通 decoder-only LLM 把整个输入送入每一层，然后逐 token 预测输出。V4.1-Flash 仍以自回归方式生成文本，但把长输入与输出生成的计算路径重新安排：用因果编码器处理输入，用解码器生成输出，再通过压缩和复用 KV cache 控制长上下文的成本。它同时采用 MoE，只激活一部分专家；图像也能进入同一模型。1017 版沿用这条路线，官方模型卡重点报告了推理、代码、智能体与视觉任务的性能和执行效率改善。[来源：基础版模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)、[1017 模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017)。

这里的“Flash”指一个总参数量仍很大的高效版本，**不等于一张消费级显卡就能训练**。

## 1. 基本范式：从标准 Transformer 走到 V4.1-Flash

先用熟悉的 decoder-only 模型做参照：提示词有 10 万 token，模型在 prefill 阶段处理它们，并把注意力所需的历史 Key/Value（KV）留在缓存里。随后每生成一个 token，模型都读取历史 KV。提示词越长，prefill 计算和缓存越贵；如果是反复读取长文档的智能体任务，成本更突出。

V4.1-Flash 采取三层分工：

1. **输入与输出路径分开。** Causal Encoder-Decoder（CED）把 40 层骨干分成 20 层因果编码器和 20 层解码器。长输入主要由编码器处理；解码器生成时所需的全局 KV 可以从编码器最终状态投影得到。官方报告的每 token 激活参数约为 prefill 8B、decode 16B；552B 是骨干的**总参数量**，不是每个 token 都运行 552B 参数。
2. **读历史时少存、少找。** Compressed Sparse Attention 2（CSA2）压缩长历史，并让不同层共享部分 KV 与索引结果；层可以采用 Full、Reindex、Reuse 三种模式。局部滑动窗口保留近期信息，全局路径从压缩历史中选择相关位置。全局主 KV 还采用 FP4 存储。官方给出的全局 KV 为约 890 字节/token，约为 V4-Flash 的四分之一。
3. **参数容量与每 token 计算分开。** MoE 的路由器在大量前馈专家中只选一小部分。官方模型卡给出 1 个共享专家、384 个路由专家，每个 token 激活 6 个路由专家；它仍要求把众多专家的权重放在设备内存或合理地分布到多设备。

这三层解决的是不同问题：CED 主要省长输入的计算，CSA2 和缓存设计主要省长历史的访问与存储，MoE 主要让总参数容量大于单 token 激活计算。模型仍以 next-token prediction 输出文本，并没有把生成方式改成扩散模型。[来源：基础版模型卡“Architecture / CSA2”](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)。

## 2. 哪些是 V4.1-Flash 的技术选择，哪些才是 1017 更新？

V4.1-Flash 的公开技术选择还包括：**SWA Bounded Replay**，只重算最近窗口以恢复未持久保存的局部 KV；**Single-Pass mHC**，优化深层网络中的多路残差连接；**Engram**，通过 token 片段查表提供条件记忆；**DSpark**，以草稿生成和验证加速推理。模型有从图像提取视觉 token 的编码器，支持图文输入。它的公开训练叙述是从多模态数据预训练，再经历 SFT、RL、on-policy distillation；模型卡称这条后训练路线没有新的算法改动，重点是自动合成智能体任务和环境的数据流水线。[来源：基础版模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)。

**不要把这些全部称为“1017 的创新”。** 1017 模型卡明确说它是 V4.1-Flash 的 *minor update*，强调在推理、代码、智能体、视觉基准上的提升，以及缩短任务执行时间、减少输出长度。比如官方表格中 Terminal-Bench 4.0 从基础版的 31.2 提升到 42.3，ProgramBench 从 20.3 到 29.1；这些是官方公布的特定评测结果，并不证明所有场景都按相同比例提升。模型卡没有充分披露 1017 相比基础版具体使用了哪些新增数据、损失函数或训练步数，因此**无法可靠地把性能增长归因于某个新算法**。[来源：1017 模型卡“Introduction / Benchmarks”](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017)。

另一个容易混淆的数字是“模型很大，但激活量只有 8B/16B”。前者决定**至少要存多少权重**，后者主要影响每 token 前向计算。做 LoRA 时基础权重虽然冻结，仍需参与前向和反向传播；不能按 8B 小模型估算整机显存。

## 3. 实际使用与微调：先确定要改变什么

1017 权重以 MIT 许可发布。官方仓库给出了专门的 prompt encoding 参考实现及 `deepseek-recipe`，而模型卡明确说**没有 Jinja 格式 chat template**。因此训练数据不能随意套用另一个模型的对话模板；工具调用、思考模式和图像内容尤其需要与官方格式一致。官方还给出了推理权重转换说明。这些是启动实验前要验证的兼容性问题，不是“安装一个通用 LoRA 脚本即可训练”的保证。[来源：1017 模型卡“Prompt Encoding / Minimal Inference”](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017)。

若目标是增强**几位特定人物**的能力，先分清具体含义：是准确回答关于这些人物的事实，还是稳定扮演他们的风格和口吻？两者的训练信号不同。事实类任务先做资料检索和评测，必要时再 SFT；角色风格可以用少量高质量对话做 LoRA-SFT。只有当你能定义可检验的偏好或奖励，例如“角色设定一致、事实有依据、避免混淆人物”，才值得进一步做 RL。否则模型很可能学会讨好奖励器，而不是真的更懂人物。

一个可执行的后训练顺序是：准备互相隔离的训练集与评测集；跑原模型基线；用人物资料构造少量高质量示范做 LoRA-SFT；再次评测；然后只对 SFT 仍解决不了、又有可靠奖励的目标运行 GRPO 或类似在线 RL。RL 每轮从当前策略采样多个回答，给奖励，依据组内相对质量更新 LoRA 参数；还需要冻结参考策略或控制偏离，监测通用能力退化。**RL 可以不需要逐 token 正确答案，却需要可信的回答级反馈。**

## 4. LoRA + RL 要多少卡、多少小时？

先给物理下限。552B 参数若按 BF16 裸权重算，约 **1.10 TB**；按 8 bit 是约 **552 GB**；按 4 bit 是约 **276 GB**，还未加量化元数据、视觉模块、激活、梯度、KV cache、通信缓冲及 RL 的 rollout 引擎。官方仓库的 `config.json` 指定 FP8 量化并有 FP4 专家配置，但**磁盘权重格式、框架的训练支持与训练时常驻显存不能简单等同于“552 GB / 卡数”**。[来源：官方配置](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/blob/main/config.json)。

为给出可讨论的量级，以下**假设**：只训练 rank 16–32 的 LoRA，冻结主模型；输入 1K、输出最多 512 token；2,000 个训练提示，每提示 4 个 rollout，做 1–2 轮，即生成约 400 万–800 万 token；以 GRPO 类算法做在线更新；上下文只用 2K 以内，不使用百万上下文；多卡高速互联，按 FP8 基础权重或经验证可训练的 4 bit QLoRA 路线。下表是根据权重占用、额外训练/推理实例和假设吞吐做的**粗略规划区间，不是该模型的公开跑分，也不是可直接照抄的部署清单**。

| GPU 类型 | 建议起步规模 | LoRA + 在线 RL 的粗估耗时 | 判断 |
|---|---:|---:|---|
| RTX 4090 24GB | 32–64 张，且必须有可用 4 bit 训练/分片方案 | 很难给可信小时数 | 单卡内存与互联都构成瓶颈；不建议作为首个实验平台 |
| A100 80GB | 16–32 张 | 约 48–200 小时 | 依赖量化训练内核和集群互联；仅是规划级量级 |
| H100 80GB | 16–32 张 | 约 24–120 小时 | FP8 与多卡吞吐可能较好；实际仍受 rollout、序列长度及框架支持影响 |
| H200 141GB | 8–16 张 | 约 18–96 小时 | 更大的显存减轻权重与 KV 压力，但不保证训练内核直接兼容 |
| B200 180GB | 8–16 张 | 约 12–72 小时 | 要依赖相应的 FP8/FP4、专家并行和 RL 实现 |

这些时间**不能当作报价**。假设 400 万输出 token，整个集群实际端到端吞吐若为每秒 100、500、1,000 个输出 token，仅采样就分别需约 11.1、2.2、1.1 小时；8M token 时间翻倍。训练前向、反向、策略同步、奖励计算、基线评测与失败重跑会继续增加耗时。时间区间还把环境调通算在内；没有在具体硬件和框架上跑过一次完整回合，就不能负责任地报出精确“几张卡、几小时”。

因此若你手上只有 1–8 张 80GB 卡，更现实的起点是**API/推理基线与小模型验证奖励设计**，或者先做 4 bit LoRA-SFT 的兼容性实验；不要按“激活 8B”推断 1 张 H100 能做这台 552B 模型的在线 RL。若确实需要 1017 模型的 LoRA + RL，先核验所选框架能否加载这种 MoE、CED、CSA2、Engram 与官方编码格式，并跑一个很小的完整训练回合，再以测得的 token/s 线性外推。人物知识的目标往往首先受资料质量和奖励可靠性限制，增加 GPU 不一定解决。
