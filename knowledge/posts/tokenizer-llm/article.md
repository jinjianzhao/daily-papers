# Tokenizer 入门：语言模型如何把文字变成 token

## 先回答一个问题：模型看到的到底是什么

我们平常说“把一句话输入语言模型”，但 Transformer 并不能直接接收文字。它接收的是一串整数，随后通过 embedding 表把每个整数查成向量。因此，在文本进入 Transformer 之前，必须先经过一个 **tokenizer**：它把字符串切成若干 token，再把每个 token 映射成词表中的 token id。

可以把流程写成：

```text
原始字符串
   ↓ tokenizer：切分 + 规范化 + 映射
token 序列，例如 ["我", "喜欢", "机器", "学习"]
   ↓ vocabulary lookup
token id，例如 [381, 9274, 1456, 6821]
   ↓ embedding
向量序列
   ↓ Transformer
下一个 token 的概率分布
```

这里的 token 不一定等于一个汉字、一个英文单词或一个完整的词。它是 tokenizer 根据自己的词表和切分规则定义的基本单位。不同模型使用不同的词表，所以同一段文字在不同模型中可能对应不同数量、不同 id 的 token。

## 为什么不直接按字符或单词切分

最简单的方案有两个极端。

**字符级**分词把每个字符作为一个 token。它几乎不会遇到“生词”，但序列会很长：一篇文章中的标点、汉字、英文字符和数字都要逐个占位。序列变长后，注意力计算和 KV cache 的开销都会增加，模型也需要用更多步才能读完同样的内容。

**词级**分词把空格分隔的单词作为 token。它对常见英文很直观，却会遇到巨大的词表和大量未登录词。例如 `unhappiness`、人名、网址、代码标识符和拼写变体很难全部预先列入词表。中文没有稳定的空格分词边界，跨语言使用时问题更明显。

子词 tokenizer 取了折中方案：常见片段可以整体保存，罕见词则拆成多个更小的片段。比如一个英文词可能被拆为 `un`、`happy`、`ness`，一个没见过的变量名也能由字符或字节片段组合出来。这样既控制词表规模，又避免完全依赖“见过完整词”。

## 从字符串到 token id：四个步骤

一个实际 tokenizer 通常包含以下步骤，但具体顺序和实现会因模型而异。

### 1. 文本规范化

输入可能含有不同的 Unicode 表示、换行符、全角/半角字符或特殊空格。tokenizer 可以选择是否进行 Unicode 规范化、大小写转换、空白处理等。规范化会影响可逆性：如果把大小写全部转成小写，就无法从 token 序列精确恢复原文。因此现代生成式语言模型通常会谨慎处理规范化，尤其是代码、数字和多语言文本。

### 2. 预分词或边界处理

有些算法先按空格、标点或字符类别划出较粗的片段；有些 byte-level tokenizer 把原始文本转成字节后再处理。空格本身是否附着在 token 上也很重要。例如某些词表会把“` hello`”（前面带空格）作为一个 token，而不是把空格和 `hello` 分开。这个选择会影响编码结果和解码时的空格恢复。

### 3. 按词表切分

切分算法根据训练得到的词表，把片段拆成一个或多个 token。算法可能是 BPE、WordPiece、Unigram，也可能是它们的变体。

### 4. 映射为整数并加入特殊 token

每个 token 查表得到一个整数 id。模型还可能需要 `<BOS>`（序列开始）、`<EOS>`（序列结束）、`<PAD>`（批处理填充）、`<UNK>`（未知片段）或对话角色标记等 special tokens。它们不是自然语言中的普通词，而是让模型识别序列边界、对话结构或批处理位置的控制符。不同模型是否使用这些 token、它们的 id 和插入位置都不统一，不能从一个模型的模板推断所有模型。

例如，假设一个小词表包含：

```text
"你"→12，"好"→35，"世界"→91，"世"→44，"界"→45，"<EOS>"→2
```

字符串“你好世界”可能编码为 `[12, 35, 91]`；如果词表没有“世界”，则可能编码为 `[12, 35, 44, 45]`。加入序列结束标记后，输入可能变成 `[12, 35, 91, 2]`。这只是示意，不代表任何具体模型的真实 id。

## 三种常见的子词算法

### BPE：不断合并高频相邻片段

Byte Pair Encoding 最初是压缩算法，后来被用于子词建模。其训练过程可以直观理解为：

1. 先把训练语料表示为较小单位（字符或字节）。
2. 统计相邻片段对的频率。
3. 把最常见的一对合并成新符号，并加入词表。
4. 重复合并，直到达到预设词表大小。

编码时，按照训练得到的合并优先级，把输入尽量合并成词表中的片段。高频词通常会形成较大的 token，罕见词则保留为多个小片段。GPT 系列中常见的是 BPE 或 byte-level BPE 的变体，但具体预分词规则、字节映射和特殊 token 仍由各模型自行定义。

### WordPiece：选择能提高整体似然的片段

WordPiece 与 BPE 的表面行为相似，也从字符片段逐步构造子词词表，但它通常依据语言模型似然增益或近似目标选择候选合并，而不是只看相邻对频率。编码时常使用最长匹配，并可能在非词首片段前加入特殊标记（例如 `##`）来表示它接在前一个片段后面。

BERT 使用了 WordPiece 风格的 tokenizer。需要注意，看到“WordPiece”并不意味着所有实现都共享同一份词表或同一套 Unicode 处理规则。

### Unigram：从候选词表中寻找概率最高的切分

Unigram 模型先准备一个较大的候选子词集合，为每个候选片段估计概率，然后逐步删除对语料解释价值较低的片段，直到达到目标词表规模。给定字符串时，它可以在多种切分方式中选择概率最高的一种，而不是一定采用贪心最长匹配。

SentencePiece 是常见的 tokenizer 工具，它可以在原始 Unicode 字符串上直接训练 Unigram 或 BPE，并把空格作为可见符号处理，从而不强制依赖外部的语言分词器。这里要区分“算法”和“工具”：SentencePiece 是实现框架，BPE/Unigram 是其中可选的建模方法。

## 训练阶段和推理阶段各做什么

在预训练之前，通常先用一批代表性文本训练 tokenizer，确定词表、合并规则或子词概率，然后固定下来。接着，预训练数据被编码为 token id，语言模型以这些 id 为输入，学习预测下一个 token：

```text
x₁, x₂, ..., xₜ  →  预测 xₜ₊₁
```

Tokenizer 本身通常不随每个 batch 通过梯度更新；它是数据预处理的一部分。模型训练的是 embedding、注意力、FFN 等连续参数，而 tokenizer 的离散切分规则在该训练阶段保持固定。若更换 tokenizer，原来的 embedding 行号、训练数据分布和上下文长度含义都会改变，通常需要重新训练或做专门的词表扩展，而不是简单替换一个文件。

推理时流程相同：先编码 prompt，再把 token id 送入模型；模型每生成一个新 token，就把它解码为字符串片段并追加到输出中。解码不一定是一步一字：一个 token 可能对应一个完整词、几个字符、一个汉字、一个字节片段，甚至是代码中的一部分。

## Tokenizer 如何影响上下文和成本

### token 数量决定“能放多少内容”

模型的上下文窗口以 token 计，而不是以字符或汉字计。同样的 10,000 个字符，在中文、英文、代码和混合文本中可能对应不同数量的 token。如果输入需要 12,000 token，而模型上下文上限是 8,192，就必须截断、分块或换用更长上下文模型。

### token 数量影响计算和计费

自回归生成每一步通常都要处理一个新 token。输入越长，prefill 阶段的计算和 KV cache 越大；输出 token 越多，decode 步数越多。API 计费也经常按输入/输出 token 统计。因此 tokenizer 不是一个只影响字符串格式的前处理器，它直接影响吞吐、延迟、显存和成本。

### 词表大小是折中

更大的词表可以让常见词用更少 token 表示，但 embedding、输出层和词表管理会占用更多参数与显存；更小的词表减少词表参数，却可能让文本被切成更多 token。多语言模型还要在不同语言之间分配词表容量。如果某种语言平均需要更多 token 表示同样的语义，模型的有效上下文和推理成本就会受到影响。

## Unicode、数字、代码和多语言的实际问题

Tokenizer 面对的并不只是“中文词”和“英文词”。

- **Unicode**：看起来相同的字符可能有不同编码形式；emoji、组合字符和罕见文字可能被拆成多个字节或子词。byte-level 设计能避免未知字符，但不代表每个视觉字符只占一个 token。
- **空格与换行**：空格可能是 token 的一部分，换行可能拥有专门 token。对代码缩进、Markdown 和对话模板而言，丢失一个空格就可能改变含义。
- **数字**：数字可以按单个数字、连续数字片段或带标点的组合切分。某些 tokenizer 对长数字的切分并不符合人类的十进制直觉，所以模型进行精确算术时仍需额外机制。
- **代码和网址**：变量名、路径、URL 往往由标点、大小写和数字组成，可能被拆得很碎。一个模型在代码上的 token 效率，不能仅凭自然语言中的表现推断。
- **多语言**：共享词表提高了跨语言复用机会，但词表容量有限。不同 tokenizer 对中文、日文、阿拉伯文等语言的平均 token/字符比可能差异很大，比较模型时应明确使用哪种 tokenizer 和统计口径。

## 一个从文本到模型输入的完整小例子

假设有一个极简词表和规则：空格标记为 `▁`，词表中有 `▁我`、`喜欢`、`机器`、`学习`、`。`，未知字符退化为单字符。输入：

```text
我喜欢机器学习。
```

可能得到：

```text
文本片段： ["▁我", "喜欢", "机器", "学习", "。"]
token id： [  18,    203,    77,    91,    6 ]
```

模型并不直接看到“喜欢”这个字符串，而是从 id `203` 查到对应 embedding 向量。训练时，若序列为 `[18, 203, 77, 91, 6]`，每个位置都会参与下一个 token 的预测目标，例如用前四个 token 预测最后一个 token。实际模型还会使用更大的词表、位置编码、对话控制符和更复杂的字节/Unicode 处理。

## 如何比较两个 tokenizer

比较时至少要固定以下条件：

1. 使用同一批文本和同一预处理方式；
2. 统计 token 数量时说明是否包含 BOS/EOS、对话模板和 padding；
3. 区分平均 token/字符、长尾样本和特定领域（代码、数学、中文）的结果；
4. 不把 token 更少直接等同于模型能力更强。切分效率只是输入表示的一部分，模型参数、数据和训练目标同样重要。

## 小结

Tokenizer 是连接自然语言和 Transformer 的接口：它决定字符串如何变成离散 id，词表和切分规则又决定模型的有效上下文、训练数据形态以及推理成本。BPE、WordPiece 和 Unigram 都是在词表规模、未知词处理和序列长度之间做折中，但它们的具体实现并没有统一标准。读论文或使用模型时，看到 tokenizer 名称还不够，还要确认词表、特殊 token、空格处理和编码版本。
