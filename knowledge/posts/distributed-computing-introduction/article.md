# 分布式计算导论：把一项工作交给很多台机器

## 先用一句话理解

分布式计算（distributed computing）研究的是：**一组通过网络连接的独立计算机，如何协作完成一项任务，并让使用者感觉它们像一个可靠的整体**。

单机程序只需要考虑本地内存、磁盘和线程；分布式程序还要面对网络延迟、消息丢失、机器宕机、数据分片和并发修改。因此，分布式计算的核心不是“机器更多”，而是要在不可靠的组件之上构造可观察、可恢复、可扩展的系统。

一个贯穿全文的例子是“统计一百亿条日志中每个单词出现了多少次”。一台机器可能放不下全部日志，也可能算得太慢；我们希望把日志拆给多台机器，最后得到一个准确、可重复的结果。

## 1. 系统由哪些角色组成

可以先把系统拆成四层：

1. **客户端**：提交查询、任务或请求。
2. **协调者（coordinator）**：决定任务怎么切分、发给谁、失败后重试什么。
3. **工作节点（worker）**：读取分到的数据，执行计算，并返回中间结果。
4. **存储层**：保存输入数据、中间数据和最终结果，通常跨多台机器复制。

这些机器通常使用消息或 RPC（远程过程调用）通信。客户端调用远程服务时，远程服务可能已经完成、正在执行、执行后回复丢失，或者根本没有收到请求；所以“调用一次”并不天然等于“执行一次”。这正是重试和幂等设计重要的原因。

## 2. 第一原则：把数据和计算分区

### 2.1 分区

分区（partitioning）是把一份大数据集切成若干可处理的片段。例如把一百亿条日志按文件范围切成 1,000 个分区，每个 worker 处理若干分区。

分区策略影响并行度和负载均衡：

- 按范围切分便于扫描连续文件，但某些范围可能特别大；
- 按哈希切分能让键较均匀地散开，但查询某个范围时需要访问更多分区；
- 热点键（例如一个特别热门的页面）可能让单个分区变成瓶颈，需要拆分或限流。

### 2.2 数据本地性

网络传输通常比本地内存或磁盘读取昂贵。调度器常优先把计算放到存有输入分片的机器附近，这叫数据本地性（data locality）。但本地性不是绝对规则：如果节点忙碌，等待它可能比跨网络读取更慢。

## 3. Map、Shuffle、Reduce：一次批处理任务的骨架

经典 MapReduce 把任务分成三个阶段：

```text
输入分片
   │
   ▼
Map：每条记录 → (key, value)
   │
   ▼
Shuffle：按 key 重分区、排序/聚合
   │
   ▼
Reduce：处理同一 key 的所有 value
   │
   ▼
最终结果
```

在词频统计中：

- Map 读取“hello world hello”，输出 `(hello, 1), (world, 1), (hello, 1)`；
- Shuffle 把所有 `hello` 发送到同一个 Reduce 分区，形成 `hello → [1,1,...]`；
- Reduce 对列表求和，得到 `hello → 2`。

Shuffle 是分布式批处理的关键代价：它需要跨网络传输、落盘、排序或哈希分组。工程上会用本地预聚合、压缩、合理分区数和数据倾斜处理来减少代价。MapReduce 论文是这一范式的经典描述，Google 的原始论文将其定义为在大规模机器集群上处理大数据的编程模型。[1]

## 4. 从“任务”到“数据流”：批处理与流处理

**批处理（batch processing）**等待一批输入准备好后运行，适合离线报表、模型训练和全量索引；它容易重放，吞吐量高，但延迟通常较大。

**流处理（stream processing）**持续接收事件，例如点击、传感器读数或支付记录，要求系统在秒级甚至毫秒级输出结果。流系统需要定义事件时间、乱序、窗口和状态：

- 滚动窗口：每 1 分钟统计一次；
- 滑动窗口：统计最近 5 分钟，每 1 分钟更新；
- 水位线（watermark）：系统认为某个时间点之前的事件基本到齐，以便关闭窗口。

批处理和流处理不是“哪个更先进”，而是延迟、成本、可重放性和结果语义之间的取舍。

## 5. 容错：机器会坏，结果不能跟着消失

分布式系统默认某个组件随时可能失败。常见故障包括：worker 进程崩溃、机器掉电、磁盘损坏、网络分区，以及请求超时但服务端其实已经完成操作。

### 5.1 任务级重试

协调者记录每个分区的状态。某个 worker 失败时，只重跑尚未确认完成的分区，而不是从头重跑整个作业。若任务有副作用（例如给账户扣款），必须设计幂等键或事务，否则重试可能造成重复扣款。

### 5.2 检查点与血缘

检查点（checkpoint）把某个时刻的状态持久化；失败后从最近检查点恢复。另一种思路是记录数据血缘（lineage）：说明某个结果由哪些输入和转换得到，需要时重新计算丢失的分区。Spark 的 RDD 就使用了“不可变分区 + 血缘”的思路，并提供 checkpoint 作为更长生命周期的恢复手段。[2]

### 5.3 复制

存储系统把同一数据写到多个节点。复制因子为 3 意味着通常需要三份副本；它提升可用性，但也增加存储成本和写入协调成本。

## 6. 一致性：多台机器看到的“现在”是否相同

如果两个客户端同时修改同一条记录，系统需要规定读写语义。常见层次包括：

- **最终一致性**：暂时可能读到旧值，但在没有新写入时最终收敛；适合部分缓存和社交动态。
- **线性一致性**：每个操作看起来像在一个全局时间轴上瞬间完成；更容易理解，但代价更高。
- **因果一致性**：有因果关系的操作保持顺序，不相关操作不必强行排序。

共识算法用于让多个节点就一个顺序或状态达成一致。Raft 将共识拆成领导者选举、日志复制和安全性规则：客户端写入领导者，领导者把日志复制到多数节点，得到多数确认后提交。[3] 共识不等于“所有机器永远同步”，而是为关键状态提供一个可证明的提交顺序。

## 7. 调度与资源管理

调度器要回答三个问题：任务放在哪些节点、资源如何隔离、失败后如何处理。实际集群通常按 CPU、内存、GPU、磁盘和网络带宽进行资源分配，并使用队列、优先级、配额和抢占策略。

调度还要避免两个极端：

- 分片太少：机器闲置，无法获得足够并行度；
- 分片太多：任务管理和 Shuffle 元数据开销变大，许多小任务反而变慢。

因此并行度应依据输入大小、单分区处理时间和集群规模来调节，而不是简单追求“机器越多越好”。

## 8. 如何判断一个分布式系统是否做得好

建议同时看四类指标：

1. **正确性**：重复执行、乱序、节点失败后，结果是否仍符合定义。
2. **延迟**：一次请求或一个窗口多久完成，尾延迟（例如 P99）是否可接受。
3. **吞吐**：每秒处理多少记录、任务每天完成多少数据。
4. **可用性与成本**：故障时能否继续服务，以及每单位结果消耗多少机器、存储和网络资源。

“扩展到更多机器后变快”还不够。若输入规模和机器数同时增加，理想的系统应保持可接受的单任务时间，这称为水平扩展（scale out）。

## 9. 新人建议的学习路线

可以用一个小型词频系统逐步练习：

1. 先在单机上实现 Map 和 Reduce，固定输入并写结果校验。
2. 把输入切成多个文件，用多进程模拟 worker。
3. 加入一个 coordinator，记录分片状态并在 worker 失败时重试。
4. 实现 Shuffle：按 key 发送到固定分区，并观察数据倾斜。
5. 给结果加入检查点，比较“从头计算”和“从检查点恢复”的时间。
6. 最后再使用一个真实框架，观察同一任务的 DAG、分区数、Shuffle 读写和失败重试日志。

这条路线把抽象概念变成可测量的行为：你能看到网络传输、并行度和故障恢复，而不只是记住术语。

## 小结

分布式计算可以归结为一条工程链：**分区数据 → 调度计算 → 交换中间结果 → 持久化状态 → 在故障和并发下给出明确语义**。MapReduce 让批处理骨架变得清晰，Spark 等系统进一步把多阶段计算组织成可复用的数据流。掌握这条链，再学习具体框架时，API 名称就能对应到它解决的系统问题。
