# LLM 入门（六）：大模型训练与推理的工程关键技术

懂得 Transformer 的计算公式，还不足以解释一个大模型为何能在成千上万张 GPU 上训练，也不足以解释它为何能同时服务很多用户。核心问题是：参数、优化器状态、训练中间结果和推理时不断增长的历史，分别放在哪里、何时计算、怎样跨设备移动？工程技术就是围绕这些数据与计算做取舍。

先看这张系统地图。箭头表示一次典型训练或请求中的数据流，不代表所有系统必须采用相同实现。

```text
训练：样本/token → 前向（参数、激活）→ 损失与反向（梯度）→ 优化器 → 新参数
         │              │                         │             │
         │          混合精度、激活重算       累积、多种并行    ZeRO/FSDP 分片
         └────────────────── 定期保存可恢复的训练检查点 ──────────────────┘
                                         ↓
推理：多个请求 → 动态调度 → prefill → KV cache → decode → 输出
                            首字前      历史存储     逐 token
                                     GQA/MLA、分页   量化、投机解码
```

## 一、训练：一张卡放不下，就重新安排“存”和“算”

训练显存不只装模型权重。反向传播还需要前向的**激活**、各参数的**梯度**以及优化器状态；显存峰值会随模型、序列长度、批大小上升。解决办法有两类：减少每卡保存的东西，或者把工作分到多卡。两者经常组合使用。

### 1. 混合精度：少用字节，但保住数值范围

若所有矩阵和中间张量都用 32 位浮点，存储和访存成本很高。混合精度让适合的矩阵乘法与张量使用 BF16、FP16 等较低精度，同时让容易累积误差的运算或某些状态保持较高精度。BF16 的指数范围较宽；FP16 训练可能需要损失缩放来避免微小梯度下溢。具体选择取决于硬件、算子和稳定性，不是把模型“一键改成 16 位”就结束。降低字节数通常能提高吞吐、降低显存压力，但数值异常仍需监测。

### 2. 梯度累积与激活重算：用时间换空间

一次大批量训练可拆成几个 **micro-batch**：每个小批做前向和反向，把梯度相加，最后只更新一次参数。这叫**梯度累积**。它降低单次激活峰值，让有效批量接近“大批一次算”；代价是要依次跑多个小批，且归一化、随机性和多卡同步方式要处理正确。它不会减少模型参数本身占用。

激活检查点（activation checkpointing，也叫激活重算）解决的是另一个显存项。通常反向要读出前向保存的每层激活；现在只保存少数边界激活，到反向时再运行相应的前向片段，换回缺失的中间结果。显存少了，计算却增加了。这里的“检查点”是内存中的计算边界，**不是**写到磁盘、供故障恢复的训练检查点。

### 3. 并行：切样本、切矩阵，或切层

**数据并行**让多个设备各持一份模型、处理不同样本，再聚合梯度。它适合扩大吞吐，但每卡仍需容纳模型及相关状态。**张量并行**把一个大矩阵或一次层计算切给多卡；单卡负担下降，不过层内需要频繁通信。**流水线并行**把不同层放在不同设备，micro-batch 像流水线一样经过各阶段；可分摊层的存储，但阶段间会传激活，并可能出现设备等待的“气泡”。三者是在不同轴上切分任务，不是互斥的三个版本；网络速度、模型形状和批大小决定组合是否划算。

优化器状态与梯度若仍在数据并行组的每卡重复存放，复制成本很大。[ZeRO](https://arxiv.org/abs/1910.02054) 和 [PyTorch FSDP](https://docs.pytorch.org/docs/stable/fsdp.html) 代表一类**分片**思路：把参数、梯度、优化器状态中的部分或全部分散保存，需要计算某层时再收集所需参数，随后释放或重新分片。于是单卡常驻显存下降，却增加收集与归还时的通信；它与“把一个矩阵的计算切开”的张量并行并不相同。

若前馈层采用混合专家（MoE），每个 token 只送到少数被选中的专家。**专家并行**把不同专家放在不同设备，使总参数容量不必全部落在每卡；路由后的 token 必须跨设备送达并在计算后送回。负载不均或网络拥塞时，理论上少算的好处可能被通信吞掉。MoE、专家并行、张量并行是不同层面的设计，不能仅凭“用了 MoE”推断训练一定更快。

### 4. 跑得久，还要能从故障中恢复

长时间训练难免遇到设备故障或数值异常。**持久训练检查点**通常保存模型参数、优化器状态、训练步数以及保证继续运行所需的随机数和数据读取进度；恢复后从最近一次可靠状态继续，而非从头开始。写得越频繁，丢失的工作越少，但存储与写入开销越大。分片训练还需要处理“各设备保存的是不同片段”这一事实：恢复时分片布局和状态必须一致或可转换。

## 二、推理：请求并发后，瓶颈从计算扩展到缓存和调度

用户给定提示词后，模型先做 **prefill**：并行处理输入 token，产生首个输出所需的状态；之后做 **decode**：每次生成一个 token，再把它作为下一步输入。prefill 往往一次涉及大量 token；decode 每步计算较小，却要反复读取参数与历史。因而两阶段对 GPU 的压力不同：长提示词影响首 token 延迟，长输出让逐 token 生成成为主要成本。

### 1. KV cache：不重算历史，但要为每个请求存历史

在 decode 第 (t) 步，当前 Query 要看过去的 Key、Value。如果每次都重新跑全部历史，重复计算会越来越多。**KV cache** 在每层保留先前 token 的 K/V，新一步只计算新 token 的 K/V 并追加。好处是避免历史前向重算；代价是每个并发请求都有随上下文长度增长的缓存。它占用显存带宽与容量，常常限制能同时服务多少长请求。

**GQA（分组查询注意力）**让多组 Query 共享较少的 K/V 头，直接降低每 token 缓存的 K/V 份数。[GQA 论文](https://arxiv.org/abs/2305.13245) 将它作为多头注意力与单组 K/V 的 MQA 之间的折中。**MLA（多头潜在注意力）**则把历史 K/V 信息压入较低维的潜在表示，再按注意力计算所需形式恢复或变换，参考 [DeepSeek-V2 报告](https://arxiv.org/abs/2405.04434)。两者都降低历史存储压力，但改变的是模型注意力结构，不能把已有任意模型的缓存直接压一下就宣称等价。压缩幅度及质量、内核效率要结合具体模型评估。

### 2. 管理缓存：分页与动态组批

即使缓存总量够大，若每个请求都提前占一段连续显存，长度未知的生成会留下空洞或预留浪费。[PagedAttention / vLLM](https://arxiv.org/abs/2309.06180) 借用分页思想：把逻辑上连续的 KV 分成块，让物理块按需分配、可以不连续，再通过映射找到它们。它主要改善**缓存内存管理与共享**，并不是减少每个 token 注意力计算量的近似算法。

传统静态批处理可能要等同一批请求全部结束，快请求也被慢请求拖住。**continuous batching（连续批处理）**则按生成步动态把新请求加入、把已完成请求移出，提高设备利用率。不过批变大也会争夺缓存、带宽和计算资源；吞吐增加，不保证每个用户的延迟都下降。

### 3. 长上下文、量化和投机解码

上下文越长，prefill 通常要做更多注意力计算，decode 也要读取更多历史 KV；窗口容量“支持 100 万 token”与“实际检索得准、首 token 很快”是三件不同的事。[FlashAttention](https://arxiv.org/abs/2205.14135) 通过分块、融合和减少高带宽显存读写来提高精确注意力的效率；它没有让标准全注意力在数学上变成线性复杂度。分块计算缓解内存流量，长输入的总工作量仍然巨大。

**量化**用更少位宽表示权重、激活或 KV，降低存储与搬运成本；量化对象不同，受益阶段也不同。权重量化可能减轻 decode 的参数读取，KV 量化可容纳更多并发或更长历史；都可能引入误差，且是否加速取决于硬件是否高效支持相应格式。

**投机解码**利用较快的小模型或草稿机制一次提出多个候选 token，再由目标模型并行验证；通过适当的接受规则，目标分布可以保持不变，详见[原始论文](https://arxiv.org/abs/2211.17192)。它想减少昂贵目标模型的串行解码轮数，而不是替代目标模型。若草稿经常被拒绝、验证成本过高，额外工作就可能抵消加速。

## 三、最终看哪三个指标？

**吞吐**是单位时间完成多少 token 或请求，反映整体服务能力。**首 token 延迟（TTFT）**从请求到第一个输出，包含排队和 prefill。**每 token 延迟（TPOT）**近似描述之后每个输出 token 等待多久，主要受 decode 调度与计算影响。它们会互相拉扯：把请求攒成更大批可能增加吞吐，却延长排队；压缩 KV 可能提高并发，但需要额外变换；投机解码可能缩短单请求输出时间，但未必提升所有负载下的总吞吐。

所以，选择工程技术前要先问：是训练**放不下**，还是推理**首字慢**、**后续字慢**、**并发不够**？同一优化只能直接解决其中一部分。模型结构、硬件互联、请求长度分布和服务目标一起决定最终方案；不存在一套对所有 LLM 都最优的固定组合。

## QA

### “我要吃”预测“苹”，下一次“我要吃苹”预测“果”时，每一层的 K/V 为什么可以复用？

关键在于 decoder-only Transformer 使用的是**因果自注意力**：位置只能看自己和左边的 token，不能看右边还没有生成的 token。因此，第一次输入“我要吃”时，模型已经算出的三个位置，在第二次输入“我要吃苹”时不会因为“苹”出现在右边就被重新修改。新 token 只能读取旧 token，旧 token 不能反过来读取新 token。

假设第一次已经处理完“我要吃”，第 (l) 层缓存了：

```text
K_l = [k_l(我), k_l(要), k_l(吃)]
V_l = [v_l(我), v_l(要), v_l(吃)]
```

生成“苹”时，第 (l) 层只需要用“苹”在这一层的输入 hidden state 计算新的 (q_l)、(k_l)、(v_l)：

```text
旧缓存：K_l、V_l
新 token：q_l(苹)、k_l(苹)、v_l(苹)
注意力：q_l(苹) 与 [K_l, k_l(苹)] 做注意力
更新：K_l ← [K_l, k_l(苹)]，V_l ← [V_l, v_l(苹)]
```

这里的“复用”不是把上一次的完整 latent 或整层输出原封不动地拿来当新 token 的表示，而是**复用旧位置已经算好的 K/V**。新 token 的 hidden state 仍然要逐层计算。到了第 (l+1) 层，模型拿“苹”在第 (l) 层得到的新 hidden state，重新计算该层自己的 (q_{l+1})、(k_{l+1})、(v_{l+1})，再读取第 (l+1) 层已有的旧缓存。每一层都有自己的一份 K/V cache：

```text
第 1 层：旧 K/V + 苹在第 1 层的新 K/V
第 2 层：旧 K/V + 苹在第 2 层的新 K/V
      ⋮
第 L 层：旧 K/V + 苹在第 L 层的新 K/V
```

所以你担心的“全局 self-attention 让 latent 变了”在标准**因果**注意力里不会发生在旧位置上：虽然新 token 的表示会汇总全局历史，但历史位置看不到新 token，历史 hidden state、历史 K/V 也就保持不变。下一次生成“果”时，过程完全一样：读取包含“苹”的缓存，只为“果”在每一层追加一组 K/V。

如果把注意力改成双向注意力，或者修改了已有前缀（例如重新排序、编辑中间 token、改变模型参数），旧位置就可能需要重算，原缓存不能直接使用。类似地，KV cache 只对同一个请求、同一套模型参数和未改变的前缀有效；它不是跨请求随意共享的普通 latent。

### prefill 是什么？

**prefill 是模型处理用户已经输入的整段 prompt 的阶段。** 例如用户输入“请解释 Transformer 的注意力机制”，tokenizer 会把这句话切成一串 token。模型可以在一次前向计算中并行处理这些输入 token，并在每一层为它们生成 K/V，写入这个请求的 KV cache。处理完成后，模型才开始生成第一个输出 token。

可以把一次请求分成两段：

```text
用户 prompt ── prefill ──> KV cache + 第一个输出 token
                              ↓
                    decode：逐 token 继续生成
```

prefill 的特点是**输入 token 多、可以并行计算**。输入越长，prefill 通常越耗时，因此它主要影响首 token 延迟（TTFT）。decode 则是“生成一个 token、把它追加到缓存、再生成下一个 token”的循环；每一步计算的 token 数少，但必须反复进行，所以它更直接影响后续 token 的速度和整体生成时长。prefill 不是一种新的模型结构，而是推理服务对“处理输入”和“生成输出”两个阶段的称呼。

### 推理服务里说的“排队”是什么？

**排队是请求已经到达服务端，但暂时还没有获得 GPU 计算资源。** GPU 同时能处理的请求数量受计算量、显存和 KV cache 容量限制。当多个用户同时发请求时，调度器会把暂时无法立刻执行的请求放在等待队列中，等正在运行的请求完成、释放显存，或者当前批次有空位时再安排它们进入 prefill 或 decode。

一次请求的时间可以粗略写成：

```text
总延迟 = 等待排队时间 + prefill 时间 + decode 时间
```

例如 GPU 正在处理一个很长的 prompt，新的请求即使只输入几个字，也可能先等待；这段等待就是排队时间。排队不等于模型在“思考”，而是服务调度器还没有让它开始计算。它会直接增加用户看到第一个 token 之前的时间，因此会反映在 TTFT 中。

实际系统通常用动态调度和 continuous batching：一个请求在 decode 时，调度器可以把另一个等待请求加入下一轮的 prefill；已经生成完的请求则移出批次。这样能提高 GPU 吞吐，但不是让所有请求都立即执行。请求太多、prompt 太长、输出太长，或者 KV cache 快要占满时，队列仍会变长。优化排队问题通常要同时看并发上限、批大小、请求长度分布、KV cache 容量和调度策略，而不能只看模型单次前向的速度。
