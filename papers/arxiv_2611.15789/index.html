VibePrevisBench: Evaluating Agentic Coding for 4D Scene Generation in Blender

来源： arXiv · HF Paper · AlphaXiv

一句话主题： 评测编码智能体在Blender中从文本等输入重建4D场景并渲染代理视频的基准研究

领域标签： 4D场景生成 / 编码智能体评测 / Blender / 视频生成 / 多模态理解

快速理解

背景与任务： 可控视频生成可利用渲染的灰盒代理视频固定布局、运动和相机，编码智能体可在Blender中重建4D场景，但缺乏同时验证视频和背后长多镜头场景的基准。

核心工作： 作者构建了VibePrevisBench基准，包含242个任务和双维度评分方法，并分析11个前沿编码智能体的表现与轨迹，指出其视觉空间理解、相机运动理解和错误修正方面的不足。

中文摘要

可控的真实世界视频生成模型可以以渲染出的灰盒代理视频（graybox proxy video）为条件，该视频固定了布局、运动与相机。编码智能体可以通过在Blender中重建4D场景来制作此类视频，但目前尚无基准能够同时检验这些视频及其背后包含多个镜头的长场景。我们提出VibePrevisBench，一个用于4D场景重建的基准：智能体将一段简述转化为可执行的4D场景，并渲染其代理视频。其242个任务涵盖四种输入类型，包括脚本、照片、续接和参考视频。每个交付结果沿两个评估维度评分。基于规则的Scene Check重新运行代码，并将导出的4D场景与隐藏的ground truth事实在九个维度上进行比较。基于VLM的Screen Check则让VLM评判器判断通过检查的事实是否能在代理视频中被识别出来。我们分析了11个前沿编码智能体的评估结果与轨迹，得出三个关键观察。第一，多模态理解能力使智能体之间产生差距，尤其是在理解空间与相机运动方面。第二，所有智能体似乎已掌握基础的相机操作与场面调度，但在具有挑战性的请求上会失败。第三，智能体会检查自己的渲染结果，却未能纠正其错误。因此，智能体需要更好的空间与相机视觉理解能力、对挑战性请求的显式检查，以及根据简述对渲染结果进行逐项验证。

详细分析

1. 任务输入、输出、功能和边界（约100字）

VibePrevisBench 的任务给定一段英文 brief \(b\)、可选的参考媒体 \(m\)（脚本、照片、续写帧或参考视频）、需要重建的地点与主体列表 \(E\)，以及输出规格 \(o\)（帧数、帧率、分辨率）。智能体输出一个可执行的 Blender Python 程序 \(p\)；运行后得到显式 4D 场景 \(S\)（主体带方向的包围盒、相机轨迹、镜头切换）并渲染出灰色代理视频 \(V\)。评测只针对 scene 与 proxy video，不检查最终外观纹理。

2. 研究动机：要解决的问题与核心 insight（约300字）

可控真实世界视频生成模型可以把“灰盒代理视频”作为条件输入，在保持布局、运动和相机不变的前提下补上真实外观。代理视频如果出错，最终真实视频也会继承这些错误，因此代理视频的质量本身至关重要。人工制作这样一段 4D previs 需要熟练的 3D 美术师和大量时间；编码智能体则可以从脚本、照片、续写帧或参考视频出发，写出 Blender 代码并迭代渲染。我们需要一个基准来系统地评估这种“从 brief 到 4D 场景再到 proxy video”的能力。

现有基准有三个缺口：第一，输入形式太窄，大多只接受文本或单一视频，缺少脚本、照片、续写等导演真实会遇到的输入类型；第二，场景内容偏静态，多数只测单物体、单镜头或短片段，无法同时测试多人轨迹、定时动作、相机运动和多镜头剪辑；第三，评估只看视频画面，不检查底层 4D 场景是否与隐藏真值一致，也不检查“屏幕上是否真的能看清”。

核心 insight 是：必须用两条互补的评估轴。Rule-based Scene Check 回答“场景本身对不对”，例如相机高度是否如 reference 一样、是否漏掉了转弯；VLM-based Screen Check 回答“观众能否在代理视频里看到这个对”。图 2 展示了这种互补性：弱智能体的高机位错误会被规则抓到，但 VLM 可能给高分；另一个弱智能体的车虽然在画面内也转弯了，却小到几乎看不见，只有屏幕检查能发现。

Figure 2：两个互补的评估维度。每个面板将参考视频与强/弱智能体的代理视频以及 Seedance 2.5 生成的对应真实世界视频进行比较。(a) Rule-based Scene Check 评估 4D 场景，并检测出弱智能体的相机过高和漏掉转弯。(b) VLM-based Screen Check 评估可见性和可辨识性：弱智能体的汽车通过了在画内和转弯检查，但距离太远无法清晰辨认。真实世界视频继承了代理视频的错误；此外，我们注意到生成的真实世界视频保留了其代理视频的错误，说明代理视频生成质量的重要性。

3. 核心贡献（约300字）

论文提出并验证了 VibePrevisBench，一个面向编码智能体的 4D 场景重建基准。

第一，它包含 242 个任务，覆盖四种输入类型：94 个脚本任务、86 个参考视频任务、39 个照片任务和 23 个续写任务；场景横跨 7 个领域、33 个地点。任务普遍要求多人、多地点、多镜头和 40 秒左右的长时长，中位每个任务有 408 条可逐项检查的规则检查，总计约 9.9 万条检查。

第二，它提出两个互补的评估维度。Rule-based Scene Check 会重新运行智能体交付的代码，导出 4D 场景并与隐藏真值事实在九个维度上比较；VLM-based Screen Check 则让 VLM 观看代理视频，只针对规则已经通过的项目检查其在屏幕上是否可辨识。这两个维度分别捕捉“场景做错”和“做了但看不见”这两类失败。

第三，论文用 11 个前沿编码智能体做了诊断，得到三个可操作的观察：多模态理解拉开智能体差距，尤其在空间和相机理解上；所有智能体掌握基础拍摄和布景，但系统性失败于挑战性请求；智能体会查看自己的渲染，却不能据此纠正错误。基于这些观察，论文提出智能体需要更好的空间/相机视觉理解、对挑战性请求的显式检查，以及逐项对照 brief 的渲染验证。

Figure 3：VibePrevisBench 概览。242 个任务涵盖四种输入类型（内环）和七个场景域（外环），跨度与任务数成比例。每张卡片是一个真实任务，包含其输入和 GPT-6 Astra 代理视频的一帧。

4. 推理阶段整体流程与基模（约400字）

推理时使用一个多模态大语言模型作为 coding agent，例如 GPT-6 Astra；它运行在 Codex CLI 或 Claude Code 中，驱动一个带 Blender 5.2 的沙盒。该基模的角色相当于“导演+程序员”：它阅读 brief，生成 Blender Python 代码，运行代码，查看渲染预览，再根据预览和 brief 的差异修订代码。推理时没有训练、微调或离线建库。

  1. 输入：用户提供的 brief（脚本/照片/续写帧/参考视频）、实体列表 \(E\) 与输出规格 \(o\)（帧数、帧率、分辨率） → 多模态 LLM 解析 brief 并生成初始 Blender Python 程序 \(p_0\) → 输出：交给沙盒执行的程序。
  1. 输入：程序 \(p_0\) → Blender 沙盒运行代码并渲染预览帧；若代码报错，则返回错误信息；若渲染成功，则返回预览图像 → 输出：错误信息或预览帧，送回给 LLM。
  1. 输入：错误信息或预览帧 → LLM 将渲染结果与 brief 对照，判断布局、人物、相机、剪辑是否符合要求；若不符或报错，则修改代码并生成新程序 → 输出：修订后的程序 \(p'\)，再次进入沙盒执行，形成反馈循环。
  1. 输入：达到用户设定预算或满足输出规格的程序 → 智能体交付最终程序 \(p\)。在评测环境中，该程序会被从零重跑，导出 4D 场景 \(S\) 和代理视频 \(V\) → 输出：最终代理视频（以及可供下游真实视频生成模型使用的 4D 场景）。

5. 核心方法：按论文 Method 小节总结（约600字）

3. VibePrevisBench（VibePrevisBench）

VibePrevisBench 的任务定义围绕“可逐项检查的隐藏真值事实”展开。每个任务由一个 brief 和一组隐藏的 GT facts 组成；facts 是能够逐条打分的陈述句。任务的目标不是生成一张好看的真实感视频，而是生成一个可执行的 4D 场景，并渲染出灰色代理视频。图 3 展示了四种输入类型和七个场景域的分布。

3.1 Task formulation（任务定义）

任务形式化为 \(\tau=(b,m,E,o)\)。其中 \(b\) 是英文 brief，\(m\) 是可选的媒体输入（脚本任务没有媒体，照片/视频/续写任务有图片或视频），\(E\) 是需要重建的地点和主体 id 列表，\(o\) 规定帧数 \(T\)、帧率和分辨率。智能体交付一个 Blender 程序 \(p\)。评测时重跑 \(p\)，逐帧读出 4D 场景 \(S=(\{x_e(t)\}_{e\in E}, c(t), \mathcal{K})\)，其中 \(x_e(t)\) 是每个实体在每帧的带方向包围盒，\(c(t)\) 是相机，\(\mathcal{K}\) 是剪辑点；渲染 \(S\) 得到代理视频 \(V\)。

隐藏真值事实 \(F=\{f_j\}\) 是评分规则。每个事实满足容差则得 1 分；度量型事实在超出容差后线性扣分。事实分为九个维度：实体、布局、空间、画面结构（picture structure）、路线、事件、相机、剪辑和物理有效性。画面结构将每个镜头的深度、法线和分割图与参考帧比较，因此只出现在有参考媒体的任务中。外观（appearance）从不评分，因为外观由下游真实视频生成模型补足。图 11 给出了四类任务各自的输入、隐藏事实和代理视频示例。

Figure 11：四类输入，每类一个任务。顶部：智能体接收的内容（脚本节选、一张照片、一个开场帧、一个参考视频）；照片、续写和视频任务还附带文本简报。中部：该任务的部分隐藏 GT 事实，每个事实标有其评分维度。底部：GPT-6 Astra 交付的代理视频的一帧，及其 Rule-based Scene Check 得分。计时事实带有容差窗口，真值无法验证的事实永远不计入。

3.2 Rule-based Scene Check and VLM-based Screen Check（基于规则的场景检查与基于VLM的屏幕检查）

交付的程序必须先通过三道门：能独立运行、能渲染完整视频、能在 Blender 中重新打开。任一门失败，两个检查都得 0 分。通过后，程序在全新沙盒中从零重跑，导出场景并渲染视频；评分只来自这次重跑，不采用智能体自己沙盒里产生的视频。

Rule-based Scene Check 先按 id 绑定主体和地点，未标记物体按类别匹配。脚本类事实是关系型事实，媒体类事实是度量型事实，并以相似变换对齐到真值空间。评分按事实分块：每块原始分 \(P_b\) 是块内所有 \(s_j\) 的均值；再用随机排列得到机会基准 \(R_b\)，并用实体存在比例 \(\kappa_b\) 修正： \[ Q_b=\mathrm{clip}\big((P_b-R_b)/(1-R_b)\big)\,\kappa_b, \] 这样随机布局得 0 分、多余杂乱会同时抬高 \(P_b\) 和 \(R_b\)、缺失实体会压低 \(\kappa_b\)。最后把块分数按预设权重合成维度分，再对任务实际涉及的维度取平均，得到 0–100 的 Scene 得分。

VLM-based Screen Check 使用 Gemini 4 作为判断器，以 2 fps 观看代理视频；照片任务还会额外给一个场景环绕渲染。VLM 先不看 brief 复述视频内容，再得到 brief 和隐藏事实中“规则已通过”的检查清单，逐项给出 no / partial / yes 三档评分。评分的四个维度是识别、动作、可见性和故事。Screen 得分是这些维度分数的均值；最终总分为 (Scene + Screen)/2。图 4 展示了单个任务从程序到两条评分路径的完整流程。

Figure 4：一个任务经过评估流水线（视频任务 M50_049，由 GPT-6 Astra 解决）。智能体在沙盒中编写 Blender Python 并检查自己的渲染结果。我们从头重新运行交付的程序。回放导出 4D 场景 S、每帧的标记框、相机和切换，并从中渲染代理视频 V。Rule-based Scene Check 将 S 与隐藏 GT 事实比较，图中显示 805 项检查中的 2 项；VLM-based Screen Check 仅针对规则通过的项目就 V 询问 VLM 判断器，图中显示 2 个判定。

3.3 Construction（基准构建）

构建分三个阶段。第一阶段是收集与筛选：用两个冻结的标注体系给场景内容和任务形式设置配额；从超过 2.7 万个源视频中先筛出 1.8k 个候选片段，再经过 VLM 检查与人工筛选得到最终片段；39 个照片任务中有 38 个来自带实测 3D 框和相机位姿的扫描数据集。第二阶段是任务构建：脚本任务采用“spec-first”方式，先确定隐藏真值场景，再写脚本，每一条可打分声明都必须引用原句；两个来自不同模型家族的盲读读者需要能从脚本中恢复这些声明，否则改写或删除。第三阶段是生成真值与检查：脚本事实来自场景规格，照片来自扫描框，视频和续写任务则用重建流水线估计各镜头、主体、相机、深度、人体和 3D 轨迹。无法被可靠验证的事实会被标记为不可计分。图 5 总结了这三个阶段。

Figure 5：VibePrevisBench 的构建方式。(1) 扫描数据集和自采视频由专家模型和 VLM 整理为七个场景域和 33 个地点。(2) 脚本以规格优先方式编写，且必须通过两位盲读者；人工选择并剪辑片段、筛选照片集。(3) 隐藏 GT 事实来自场景规格、4D 重建或扫描的 3D 框，人工在九个维度上审查生成的检查项。

3.4 Statistics（统计数据）

VibePrevisBench 包含 242 个任务：94 个脚本、86 个参考视频、39 个照片、23 个续写；每个领域含 19–46 个任务，每个地点含 3–13 个任务。brief 长度中位数 368 词；输出视频时长中位数 40 秒。88% 的任务有两个或更多镜头，80% 有移动相机，79% 有两个或更多人，69% 有人物与手部物体交互，61% 涉及两个或更多地点；71% 同时要求多镜头、移动相机和多人。每个任务的规则检查数量从 20 到 2,175 不等，中位数 408，总计约 9.9 万条；事件类检查占 57%，但最终分数按维度平均而不是按检查数平均，因此事件不会主导总分。

Figure 6：任务统计，按输入类型堆叠；虚线标记中位数。(a) 简报长度（词数）；脚本长度集中在约 600、800 和 1,200 词。(b) 输出长度；照片任务每张照片显示 12 帧，然后环视该地点 8 秒。(c) 具有每种布景需求的任务数量和比例，按输入类型拆分。(d) 每个任务的规则检查数，对数刻度；一个事实可扩展为多项检查，例如成对事件顺序。

6. 局限性和展望（约300字）

论文明确指出的限制主要有四点。第一，没有任何智能体接近解决该基准：在 242 个任务中，只有 35 个任务有某个智能体达到 Rule-based Scene Check 90 分；即使每任务取 11 个智能体中的最优，整体总分也只有 80.6。这说明任务本身仍未被现有模型攻克。第二，基准只评估灰色代理视频和 4D 场景，不检查外观纹理，因为外观由下游真实视频生成模型负责，因此它不能衡量最终成片的真实感。第三，部分视频任务的隐藏真值事实无法被自动重建流水线可靠验证，被标记为不可计分；这意味着基准覆盖的是“可验证”的子集，而不是完整的视觉内容。第四，基准建设过程中，部分参与评估的模型家族也帮助生成脚本、筛选片段或估计真值，论文虽然做了盲读、人工审查和相关性检查，但仍不能完全排除轻微的 self-preference 或 judge 自身家族的偏差。

可以谨慎推断的限制包括：任务时长以中位 40 秒、最长 60 秒为界，尚未覆盖更长的多幕叙事；场景只来自 7 个领域和 33 个地点，对其他类型场景的泛化能力未知；评测依赖 Gemini 4 作为 VLM 判断器，屏幕检查结果可能随 VLM 换代而变化。

展望方面，论文的三条观察直接指出了改进方向：让编码智能体更准确地理解空间与相机运动，对低角度、环绕、多机位等挑战性请求增加显式检查，并在交付前逐项核对渲染画面与 brief。未来也可以把 Screen Check 从离线评估器变成智能体自身的验证工具，或把基准扩展到更长故事、更多输入模态和真实感外观评估。
