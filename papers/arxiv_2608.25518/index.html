Agentic Game Development as a Verifiable Trajectory Data Engine for Scaling World Models

一句话主题： 利用游戏开发中的引擎与人工验证训练世界模型

领域标签： 世界模型 / 强化学习 / 游戏开发

快速理解

背景与任务： 仅靠爬取视频和模糊奖励信号难以有效扩展空间世界模型。

核心工作： 提出RLHEV，用引擎密集信号和人类验收反馈构建可验证的后训练数据引擎。

中文摘要

扩展世界模型的一种常见策略是使用更多爬取的视频和更多算力进行训练。我们认为，这一策略效率低下：扩展世界模型还需要一种能够提供有根据奖励信号的递归数据引擎。代码智能体的成功说明了这一点为何重要。由于代码是可执行的，编译器和运行时可以为大语言模型（LLM）的强化学习（Reinforcement Learning, RL）后训练提供高质量奖励。相比之下，空间生成仍在很大程度上依赖诸如 CLIP 分数之类的模糊代理指标。这些信号模糊且存在偏差，因而难以支持 RL 后训练。与这些相比，游戏开发为面向空间的世界模型提供了一个缺失的奖励环境。由游戏引擎编码的场景是一种可执行的世界规范：引擎可以高效检查碰撞、物理、可导航性和有界可玩性，而开发者则通过判断场景是否应被接受来提供全局验证信号。游戏开发还为 RL 后训练提供了真实世界的长时程轨迹数据。因此，我们提出了带有人类—引擎验证的强化学习（Reinforcement Learning with Human-Engine Verification, RLHEV），这是一种后训练范式，将密集的引擎信号与来自开发过程的隐式人类接受反馈相结合。

详细分析

下面我按“给懂 Transformer/强化学习基础、但不熟悉游戏开发与世界模型数据引擎的低年级博士生”的方式讲这篇论文。

1. 任务输入、输出、功能和边界

这篇论文讨论的不是一个单纯的“视频生成模型”或“3D 生成模型”，而是一个更偏系统性的任务：

如何把游戏开发过程变成一个可验证的数据引擎，用来训练能够构建、理解、修改虚拟世界的世界模型。

论文提出的系统叫 AWoMo：Agentic World Model，可以理解为一个“会在游戏引擎里搭世界、查错误、修错误、并从人类开发者反馈中学习的智能体”。

任务输入

输入可以包含多种信息：

  1. 文本意图

例如： “创建一个可以从入口走到宝箱房间的地下城场景。” “把这个 Unity 场景中的桥加宽，保证玩家可以通过。”

  1. 参考图像或多模态素材

比如一张场景概念图、已有资产截图、布局草图。

  1. 已有游戏场景或资产状态

例如 Unity / Unreal / Godot 中的场景文件、对象位置、碰撞体、材质、脚本、导航网格等。

  1. 设计约束

例如：

  • 玩家必须能从 A 点走到 B 点；
  • 物体不能穿模；
  • 场景必须能加载；
  • 物理模拟不能爆炸；
  • 某个任务必须在有限步数内可完成。

任务输出

输出不是一张图片，而是更“可执行”的东西：

  1. 场景程序或场景编辑动作

例如添加物体、移动物体、修改碰撞体、调整脚本、重建导航网格。

  1. 可在游戏引擎中运行的场景状态

也就是 Unity / Unreal / Godot 可以加载、渲染、模拟和测试的世界。

  1. 修复轨迹

包括模型做了什么、引擎报了什么错、人类是否接受、模型如何修复。

  1. 训练数据

每次开发过程都会被保存成“状态—动作—检查—人类反馈—修复”的轨迹，用来继续训练下一代模型。

系统功能

AWoMo 的核心功能包括：

  • 根据人类意图生成或修改游戏场景；
  • 调用游戏引擎执行检查；
  • 根据引擎错误定位问题；
  • 自动提出修复；
  • 等待人类开发者最终接受或拒绝；
  • 把整个过程转为可训练数据；
  • 用这些数据进行后训练，尤其是强化学习式的改进。

边界：它不声称解决什么？

这点很重要。

论文没有声称游戏引擎可以自动判断所有空间质量。比如：

  • 场景是否“有艺术感”；
  • 氛围是否符合剧情；
  • 玩家是否觉得好玩；
  • 关卡节奏是否合理；
  • 风格是否符合产品方向。

这些仍然需要人类判断。

游戏引擎能可靠检查的是更结构化、更局部、更可执行的性质：

  • 场景能不能加载；
  • 脚本有没有运行错误；
  • 物体是否发生碰撞穿插；
  • 物理模拟是否稳定；
  • 玩家是否能走通；
  • 自动测试智能体是否能完成某个目标。

所以论文的边界是：

引擎提供低成本、可重复、局部且结构化的验证；人类提供最终的全局接受判断。

2. 论文要解决的问题以及问题发生的具体原因

论文要解决的问题可以概括为：

当前世界模型主要靠更多视频、更多 3D 数据、更多算力来扩展，但缺少像代码领域那样便宜、可靠、可反复使用的奖励信号，因此很难进行高效的强化学习后训练。

为什么代码智能体发展快？

论文用代码智能体作类比。

代码有一个很强的性质：可执行。

模型生成一段代码后，可以马上运行：

  • 编译器能检查语法错误；
  • 单元测试能检查功能；
  • 运行时能暴露异常；
  • 静态分析器能发现潜在问题；
  • 开发者最终决定是否接受这个补丁。

也就是说，代码智能体有一个“双重验证”机制：

  1. 机器验证：编译器、测试、运行时；
  2. 人类验证：开发者判断是否真的符合需求。

这使得代码模型可以做强化学习后训练：模型生成候选代码，执行后得到奖励或错误，再更新模型。

为什么空间生成和世界模型困难？

视频生成、3D 生成、世界模拟通常没有这么好的验证器。

例如一个视频模型生成一个片段，我们可以问：

  • 物体被遮挡后是否保持同一身份？
  • 桌子上的杯子是否真的受重力约束？
  • 透视是否一致？
  • 人物走路时脚是否滑动？
  • 门是否真的通向另一个空间？

这些问题很难通过一个便宜、确定的函数来判断。

当前常用评价信号包括：

  • CLIP 相似度；
  • FVD 等分布距离；
  • MLLM-as-judge，多模态大模型打分；
  • 人类偏好标注。

论文认为这些信号有三个具体问题。

原因一：奖励信号模糊

CLIP 分数高，不代表 3D 结构正确。 一张图看起来像“房间”，不代表里面可以导航，也不代表门真的能打开。

原因二：奖励信号有系统偏差

如果一个代理评价器偏好某种纹理、构图或常见模式，模型会学会投机取巧。 这就是奖励黑客：模型提高代理分数，但真实质量没有提高，甚至变差。

原因三：只有最终输出标签，缺少过程监督

很多空间生成任务只评价最终结果，比如“一张图好不好”“一个视频像不像”。 但模型不知道：

  • 哪一步放错了；
  • 哪个碰撞体出问题；
  • 哪个区域不可达；
  • 哪次修复有效；
  • 人类为什么拒绝。

因此它很难像代码模型一样从局部错误中迭代改进。

论文把这个问题称为一种 unverifiability tax，可以翻译成“不可验证性税”： 由于缺少便宜可靠的验证信号，空间智能只能靠更多数据、更多人工标注、更多算力来弥补，训练效率低。

3. 核心 insight 与贡献

核心 insight

论文的核心洞察是：

游戏开发天然提供了空间世界模型缺少的验证环境。 一个游戏场景不是普通图片，而是一个可执行的世界规格说明；游戏引擎可以运行它、检查它、模拟它、测试它。

比如 Unity 场景中包含：

  • 物体位置；
  • 网格；
  • 材质；
  • 碰撞体；
  • 刚体；
  • 脚本；
  • 导航网格；
  • 触发器；
  • 摄像机；
  • 光照；
  • 玩家控制器。

这些不是静态像素，而是可以被引擎执行的结构化对象。

因此游戏引擎可以像“空间领域的编译器和运行时”一样，给世界模型提供反馈：

  • 加载失败：类似代码编译失败；
  • 脚本报错：类似运行时异常；
  • 碰撞穿插：类似违反几何约束；
  • 导航不可达：类似测试不通过；
  • 自动玩家无法完成目标：类似功能测试失败。

但游戏引擎不能替代人类。 所以论文提出 Human-Engine Verification：人类—引擎联合验证。

Figure 1：从 subjective reward proxies 到 human-engine verification loop。传统 spatial-data pipelines 将稀疏的人类或模型标注转为噪声较大的 final-output rewards。相反，game-development loop 可把 human intent 和反馈与 engine 执行、development trajectories、rendered evidence 以及 localized verifier failures 结合起来，使未来的构建者既能基于 grounded checks，也能基于 traces 而非仅 final artifacts 的 developer judgment 来改进。

主要贡献

论文的贡献可以分成四类。

贡献一：提出“可验证性瓶颈”

作者认为，世界模型扩展的关键瓶颈不只是数据量和模型规模，而是反馈信号的质量。

没有可靠奖励，就难以做稳定的强化学习后训练。

贡献二：提出 RLHEV

RLHEV 是 Reinforcement Learning with Human-Engine Verification，即“基于人类—引擎验证的强化学习”。

它结合两类奖励：

  1. 引擎奖励：密集、便宜、可重复，检查局部结构问题；
  2. 人类接受反馈：稀疏、昂贵，但代表最终任务是否合格。

贡献三：提出 AWoMo

AWoMo 是一个 agentic world model，也就是嵌入游戏开发流程中的世界构建智能体。

它不只是生成一个结果，而是参与完整循环：

提议编辑 → 渲染 → 引擎检查 → 修复 → 人类审核 → 存储轨迹 → 继续训练。

贡献四：提出 UWDP 轨迹协议

UWDP 是 Unified World-Development Protocol，统一世界开发协议。

它把游戏开发过程中的文本意图、场景状态、动作、引擎输出、渲染证据、人类反馈、修复关系都保存下来。

重点是： 论文认为“开发轨迹”比“最终资产”更有训练价值。

4. 使用的基模，以及从输入到输出的整体流程

使用的基模

论文没有把重点放在某个全新 Transformer 架构上，而是把 AWoMo 描述为一个围绕多模态世界模型构建的系统。

可以把它理解成：

  • 底层是一个多模态基础模型，能够处理文本、图像、场景结构、引擎日志；
  • 外层是一个智能体框架，能够调用工具、执行动作、读取反馈；
  • 环境是 Unity / Unreal / Godot 等游戏引擎；
  • 训练方式包括监督微调、偏好学习、基于引擎和人类反馈的强化学习后训练。

它更像“代码智能体 + 游戏引擎 + 多模态世界模型”的组合。

从输入到输出的整体流程

整体流程如下。

第一步：接收设计意图

输入任务 brief，例如：

生成一个小型迷宫，玩家从入口出发，必须能到达出口，中间不能有不可跨越障碍。

系统解析出：

  • 关键对象：入口、出口、墙、地面、玩家；
  • 空间关系：入口连接路径，出口可达；
  • 约束：不能封死路径，碰撞体不能阻塞玩家；
  • 验证目标：导航网格连通，自动测试玩家可到达出口。

第二步：生成或编辑场景程序

AWoMo 产生动作，例如：

  • 添加墙体；
  • 摆放地板；
  • 设置碰撞体；
  • 烘焙导航网格；
  • 添加目标触发器；
  • 调整物体坐标。

这一步输出的是游戏引擎可执行的场景，而不是一张静态图。

Figure 3：用于理解与生成的 shared executable scene-program representation。Game creation 将 human world understanding、design intent、constraints 和 playable experience 映射到模型的理解与生成能力中。生成将 text intent、design goals 或 task specifications 映射为 scene program；理解则反向读取同一对象。engine 通过 rendering、physics rollouts 和 temporal consistency 对其进行检查，而 humans 判断生成的世界是否保留 intent 和 workflow value。

第三步：游戏引擎执行检查

引擎运行场景并返回检查结果，例如：

  • 场景能否加载；
  • 是否有脚本错误；
  • 是否有物体穿插；
  • 物理模拟是否稳定；
  • 玩家代理是否能走到目标；
  • 是否出现软锁，即玩家被困住无法继续。

这些检查产生密集反馈。

第四步：模型根据错误修复

如果引擎发现问题，AWoMo 根据错误日志和渲染证据提出修复动作。

例如：

  • 如果桥太窄导致导航失败，就加宽桥；
  • 如果箱子挡住门，就移动箱子；
  • 如果碰撞体过大，就缩小碰撞体；
  • 如果脚本报错，就修复引用或参数。

第五步：人类开发者审核

当引擎检查基本通过后，人类判断：

  • 是否符合 brief；
  • 是否可读；
  • 是否有设计价值；
  • 是否风格合适；
  • 是否能进入实际开发流程。

人类给出接受、拒绝或修改意见。

第六步：保存完整轨迹并训练

系统保存每一步：

  • 初始意图；
  • 中间状态；
  • 动作；
  • 引擎检查；
  • 渲染截图；
  • 人类反馈；
  • 修复链接；
  • 最终结果。

这些数据用于训练模型。

Figure 7：protocol traces 保留了 final snapshots 中缺失的 process data。final scene 只记录 terminal state，而 trace 记录 intent、intermediate scene states、failed checks、repair edits、validation outcomes 和 engine rewards。这个 object-linked sequence 为 asset diagnosis 和 repair 提供训练目标。

5. 每个关键机制为什么需要、具体怎么做、得到什么

5.1 Human-Engine Verification：为什么需要？

单独依赖人类反馈太贵。 每个碰撞错误、导航错误、脚本错误都让人类检查，成本很高。

单独依赖引擎反馈又不够。 引擎能判断“能不能走通”，但不能判断“这个关卡是否有趣”“是否符合叙事”。

所以论文提出人类—引擎分工：

信号来源擅长判断不擅长判断
游戏引擎碰撞、物理、导航、脚本、加载、局部可玩性审美、叙事、设计意图、生产价值
人类开发者是否符合目标、是否值得接受、是否有设计价值大量局部机械错误检查

具体怎么做？

论文给出一个奖励抽象：

模型选择候选输出 \(y\)，目标是最大化：

  • 人类接受效用；
  • 减少引擎检查惩罚；
  • 满足硬性引擎门槛。

简单解释就是：

最好的人类评分高； 碰撞、导航、物理等错误少； 必须通过若干硬性测试，比如能加载、能运行、目标可达。

其中：

  • \(U_H(x,y,h)\)：人类审核分数；
  • \(C_i(x,y)\)：第 \(i\) 个引擎诊断指标，比如碰撞深度；
  • \(\phi_i\)：把诊断指标变成惩罚；
  • \(G_j(x,y)\)：硬性门槛，通过为 1，不通过为 0。

得到什么？

这种机制带来三个好处：

  1. 训练奖励更低噪声

碰撞检查比“图像看起来是否合理”更确定。

  1. 错误更可定位

引擎能告诉你哪一类检查失败，而不是只给一个模糊低分。

  1. 人类反馈更省

人类不用逐个检查低级错误，只需要审核通过自动过滤后的候选。

Figure 2：unverifiable spatial generation 中的 fuzzy reward 与 game development 中的 human-engine feedback。上方 pipeline 表明，model-as-a-judge 和 human aesthetic variance 可能产生含糊的 rewards 与 performance bottleneck。下方 pipeline 将 assets 转为 executable worlds：game engine 和 internal test suites 暴露 local failures，rendered evidence 支持 review，developer 提供最终的接受信号。

5.2 AWoMo：为什么需要？

如果只训练一个离线生成模型，它生成失败后不会自然学到如何修复。 论文希望世界模型像代码智能体一样嵌入真实工作流：

  • 会调用工具；
  • 会观察运行结果；
  • 会根据错误迭代；
  • 会存储过程数据；
  • 会用过程数据继续训练。

这就是 AWoMo 的作用。

具体怎么做？

AWoMo 有四个接口。

1. 意图接口

接收：

  • 文本 brief；
  • 设计约束；
  • 参考图；
  • 已有场景上下文。

2. 动作接口

输出：

  • 场景程序；
  • 资产编辑；
  • 工具调用；
  • 修复动作。

3. 验证接口

记录：

  • 加载检查；
  • 碰撞检查；
  • 物理稳定性；
  • 导航连通性；
  • 脚本执行；
  • 自动 playtest。

4. 审核接口

记录人类：

  • 接受；
  • 拒绝；
  • 修改意见；
  • 对最终用途的判断。

得到什么？

AWoMo 得到的不只是“最终场景”，而是高价值轨迹：

哪个意图导致哪个动作，哪个动作造成哪个错误，哪个修复解决了错误，人类最后是否接受。

这类数据适合训练：

  • 下一步编辑预测；
  • 错误诊断；
  • 修复策略；
  • 奖励模型；
  • 强化学习策略。

5.3 UWDP：为什么需要？

普通游戏开发数据分散在很多地方：

  • 场景文件；
  • 截图；
  • 编辑器日志；
  • QA 记录；
  • Git 提交；
  • 人类评论；
  • 测试报告。

如果不统一格式，模型很难学习开发过程。

论文认为，仅有最终快照不够，因为最终场景只告诉你“最后是什么样”，不知道“为什么变成这样”。

具体怎么做？

UWDP 把每一步记录成：

\[ u_t = (b, o_t, s_t, a_t, g_t, v_t, h_t, \rho_t) \]

解释如下：

  • \(b\)：设计意图；
  • \(o_t\)：对象、关系或场景区域 ID；
  • \(s_t\)：当前状态，包括空间、语义、物理字段；
  • \(a_t\)：编辑或工具动作；
  • \(g_t\)：引擎或测试输出；
  • \(v_t\)：渲染证据，比如截图或视频；
  • \(h_t\)：人类审核决定或评论；
  • \(\rho_t\)：修复关系、置信度、成本、剩余风险。

得到什么？

UWDP 让训练数据从“静态样本”变成“因果过程样本”。

模型可以学到：

  • 什么动作容易导致穿模；
  • 什么修复能恢复可导航性；
  • 哪些引擎错误通常会被人类拒绝；
  • 什么类型的候选即使通过引擎测试也不符合人类意图。

5.4 RLHEV：为什么需要？

预训练让模型学会模仿已有数据，但不一定学会满足可执行约束。

比如模型可以生成“看起来像桥”的结构，但：

  • 玩家走不上去；
  • 桥和地面之间有缝；
  • 碰撞体不匹配；
  • 导航网格断开；
  • 物理对象掉落。

RLHEV 的作用是用引擎和人类反馈做后训练，让模型更偏向生成“可运行、可审核、可接受”的世界。

具体怎么做？

论文实验中把奖励分为几类：

  1. Fuzzy proxy reward

类似 CLIP 或模型打分。

  1. Engine reward

来自 Unity 检查，例如结构有效性。

  1. Human reward

来自人类接受/拒绝标签。

  1. Full RLHEV reward

论文中使用： \[ 0.65 \times \text{human} + 0.35 \times \text{engine} \]

也就是说，人类最终接受更重要，但引擎检查也提供稳定的局部监督。

得到什么？

实验中 Full RLHEV 在 UnitySceneBench 上表现最好。 这支持作者的主张：人类反馈和引擎反馈结合比单独使用模糊代理或单独引擎信号更有效。

6. 主结果、消融结果、可视化结论及证据边界

论文实验主要围绕三个问题：

  1. 人类—引擎反馈是否比模糊代理更好？
  2. 这种训练是否能迁移到分布外或其他引擎？
  3. AWoMo 生成的环境数据是否能帮助具身智能体训练？

6.1 UnitySceneBench：人类—引擎反馈的主结果

论文构建了一个 UnitySceneBench，用于 Unity 资产编辑候选的多模态理解/分类评估。

输入包括：

  • 文本编辑提示；
  • Unity 资产和上下文特征；
  • 参考图像特征；
  • 结构化布局信息。

主要指标是 Primary：

\[ 0.45 \times \text{balanced accuracy}

  • 0.25 \times \text{accuracy}
  • 0.20 \times \text{F1}
  • 0.10 \times \text{AUC}

\]

它综合考虑类别平衡准确率、普通准确率、F1 和 AUC。

论文比较的方法包括：

  • Zero-shot CLIP；
  • Fuzzy Proxies Baseline；
  • SFT Baseline；
  • Offline RLHF；
  • Engine-based RLVR；
  • Full RLHEV。

结果：

  • Full RLHEV 取得最高 best-of-eight primary score：0.681；
  • accuracy：0.665；
  • balanced accuracy：0.665；
  • F1：0.733；
  • AUC：0.690；
  • 比最强非 Full baseline 高 +0.098 primary score；
  • accuracy / balanced accuracy 高 +0.120。

注意：这里使用了 best-of-eight 视角，也就是八个随机种子中取最佳结果。论文也另外报告了均值和方差曲线。

6.2 扩展数据量后的结果

论文还改变训练样本数，观察不同方法随着数据增加的表现。

在生成侧任务上：

  • Full RLHEV 在 640 个训练样本内达到 0.8106 generation quality；
  • 在完整 720 个训练样本下达到 0.8197；
  • Engine-based RLVR 为 0.7934。

这说明仅有引擎反馈不如人类—引擎联合反馈。

6.3 消融结论

从实验设计看，核心消融是比较不同奖励来源：

方法使用信号结论
Fuzzy Proxies模糊代理奖励不如可验证信号稳定
SFT模仿训练能学到样本模式，但缺少反馈优化
Offline RLHF人类偏好/接受反馈有帮助，但缺少密集结构反馈
Engine-based RLVR只有引擎反馈能提升结构有效性，但不一定符合人类意图
Full RLHEV人类 + 引擎整体最好

消融支持论文核心主张：

引擎反馈负责局部结构正确，人类反馈负责最终任务合格；两者互补。

6.4 OOD 泛化与跨引擎迁移

论文还测试了源域预训练是否有助于目标域适配。

设置是：

  • target-only scratch：只在目标域训练；
  • target-adapted transfer：先在源域训练，再在目标域适配。

结果：

  1. Unity 分布偏移：
    • scratch：0.25
    • transfer：0.75
  1. Unity → Unreal：
    • scratch：0.25
    • transfer：0.35
  1. Unity → Godot：
    • scratch：0.15
    • transfer：0.35

结论是：

  • 同一引擎内的分布迁移提升较明显；
  • 跨引擎迁移也有正信号，但幅度较小。

这里需要特别注意证据边界： 跨引擎质量没有统一的引擎原生标量，所以论文用了 rubric-based MLLM-as-a-judge 作为评估工具，并称人工复核过。也就是说，这部分评价仍然没有完全摆脱模糊评估，只是作者强调它没有作为训练奖励，而是作为审计后的评估指标。

6.5 具身智能体诊断实验

论文还测试 AWoMo 生成的环境数据是否能帮助具身策略训练。

基准包括：

  • R2R：视觉语言导航；
  • Gymnasium MuJoCo：连续控制；
  • D4RL Gym-MuJoCo：离线强化学习控制任务。

比较：

  • 原始 baseline；
  • naive augmentation；
  • AWoMo-augmented training。

结果是 AWoMo 增强训练相对原始 baseline 有提升：

  • R2R success rate：+0.79%
  • Gymnasium MuJoCo rollout return：+9.96%
  • D4RL Gym-MuJoCo normalized score：+48.43%

论文据此认为，agentic 环境生成可以作为具身策略训练的数据增强来源。

但要注意：

  • R2R 的提升很小；
  • MuJoCo 和 D4RL 的提升更明显；
  • 这些是 diagnostic settings，即诊断性实验，不等于大规模真实泛化已被证明。

7. 局限性和最终判断

局限性一：实验规模仍然偏小

UnitySceneBench 的训练样本规模是数百级别，完整预算为 720 个训练实例。 这对于证明一个“可扩展数据引擎”来说还很早期。

论文自己也承认结果是 pilot studies / diagnostic studies，需要更大规模验证。

局限性二：跨引擎评价仍依赖 MLLM-as-a-judge

论文批评模糊代理奖励，但跨引擎实验又不得不用 MLLM-as-a-judge 作为统一评价尺度。

作者的辩护是：

  • 它只用于评估，不用于训练；
  • 使用统一 rubric；
  • 经过人工检查。

但这仍然意味着跨引擎结论的证据强度弱于 Unity 内部引擎检查结果。

局限性三：游戏引擎验证只覆盖部分空间性质

游戏引擎能检查：

  • 碰撞；
  • 物理；
  • 导航；
  • 脚本；
  • 有界 playability。

但它不能自动判断：

  • 艺术风格；
  • 叙事合理性；
  • 玩家体验；
  • 创意质量；
  • 真实世界物理是否完全准确。

因此 RLHEV 不是“全自动真值机器”，而是“局部可验证 + 人类最终判断”的折中。

局限性四：虚拟世界和真实世界仍有差距

游戏引擎中的物理、材质和交互规则是人工设计的。 它们不完全等于真实世界。

所以用游戏开发轨迹训练出来的世界模型，是否能稳定迁移到真实机器人、真实视频理解、真实物理预测，还需要进一步研究。

局限性五：人类反馈仍是瓶颈

虽然引擎可以过滤大量低级错误，但最终接受仍然依赖人类。 如果要规模化，需要解决：

  • 人类审核成本；
  • 审核标准一致性；
  • 不同开发者偏好差异；
  • 任务 brief 的可解释性；
  • 数据隐私和版权问题。

最终判断

这篇论文最有价值的地方不是某个模型结构，而是提出了一个清晰的数据与反馈范式：

世界模型要继续扩展，不能只靠更多爬取视频；还需要能产生可靠奖励的工作流。游戏开发可能正是这样一个工作流，因为游戏场景是可执行的，游戏引擎能提供局部验证，人类开发者能提供最终接受信号。

它的论证强项是：

  • 类比代码智能体很自然；
  • 明确区分了引擎验证和人类判断；
  • 把“最终资产”转向“开发轨迹”作为训练数据；
  • 实验初步支持 human + engine 比单独模糊代理或单独引擎反馈更好。

它的证据边界是：

  • 规模还小；
  • 跨引擎评价仍不够硬；
  • 具身实验是诊断性结果；
  • 尚未真正证明递归自我改进可以长期稳定发生。

总体来说，这篇论文可以看作一篇“研究议程 + 初步实证”的文章。 它提出的方向值得重视：把游戏开发过程变成世界模型的可验证轨迹数据引擎。如果后续能在更大规模、多引擎、多任务、真实人类开发流程中复现这些收益，那么它可能成为空间世界模型后训练的一条重要路线。
