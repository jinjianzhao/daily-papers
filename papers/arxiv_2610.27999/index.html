Matrix-Game 4.0: Harnessing Video Models for Real-Time Playable Game Worlds

来源： arXiv · HF Paper · AlphaXiv

一句话主题： 视频模型驱动的实时可玩游戏世界生成

领域标签： 游戏生成 / 视频模型 / 实时交互

快速理解

背景与任务： 从可控视频到可玩游戏需要持久状态、可执行规则和低延迟交互，现有方法难以兼顾。

核心工作： 设计分离游戏执行与视觉生成的框架，结合轻量引擎、编码智能体和自回归视频渲染器，实现低延迟高帧率可定制游戏。

中文摘要

从可控视频迈向真正可游玩的游戏世界，需要持久的世界状态、可执行的游戏规则和低延迟交互。我们描绘了下一代Matrix-Game的路线图，通过一个可执行的游戏框架（executable game harness）将游戏执行与视觉生成分离，并推出Matrix-Game 4.0作为首个基于该设计的系统。一个轻量级游戏引擎维护世界状态并执行交互规则，一个多模态编码智能体将玩家想法转化为游戏代码和动态场景描述（dynamic scene captions），一个基于自回归视频模型的渲染器将引擎渲染的低多边形代理（low-poly proxies）转换为精细视觉画面，并以动态描述和记忆引用为条件。该框架为视觉生成提供持续引导，并支持通过自然语言创建和修改场景及游戏玩法。我们的渲染器在对齐的低多边形与高保真视频对上进行训练，并蒸馏为一个因果生成器，以四帧为块、每块一或两次去噪步骤进行生成。结合针对性的推理优化，Matrix-Game 4.0可在单个NVIDIA RTX5090上实现480p、60 FPS的游戏运行，按键到显示的延迟为112ms。单步生成可实现83FPS的稳态吞吐量，峰值GPU显存占用为18.2GiB。在固定提示词下，稳态吞吐量在RTX5080上也可达到67FPS，在RTX5070Ti上达到58FPS。我们展示了具有引擎强制机制（engine-enforced mechanics）的可定制射击游戏和驾驶游戏，并发布代码、模型权重和低多边形游戏资源，以支持可游玩游戏世界的研究与创作。

详细分析

1. 任务输入、输出、功能和边界（约100字）

输入是玩家的键盘/鼠标操作，以及用自然语言给出的创建或修改请求；输出是实时的高保真游戏视频帧。系统功能上把“游戏逻辑”和“视觉生成”分离：轻量游戏引擎负责持久世界状态、碰撞/生命值等规则，视频渲染模型只负责把低多边形代理绘制成高保真画面。当前边界是面向射击/驾驶类场景，在 480p、60 FPS 和单张消费级 GPU 上运行。

2. 研究动机：要解决的问题与核心 insight（约300字）

现有交互世界模型把生成网络同时当作世界状态、规则和视觉的载体，导致四个问题：没有外部持续校正，模型输出一旦偏离就难以拉回；小误差在自回归中累积，长时间后场景崩溃；历史帧只会不断堆积，没有压缩成紧凑记忆；玩法机制只停留在导航和环境反应，缺少可执行规则与持久后果。作者还指出，扩散模型学到的是统计相关性，并不等于因果/物理理解；语言到视频的映射本质上更像一种“符际翻译”，视频生成器更像一个渲染器，而不是完整的视觉世界模型。

因此，关键 insight 是：不要试图让视频模型记住世界，而是把“游戏如何运行”和“游戏看起来如何”分开。用一个外部可执行框架承担状态维护和规则执行，让引擎持续给出低多边形代理和结构化控制信号，再让视频模型只负责把几何草图渲染成高保真画面。这样，模型每一帧都有外部引导，不需要隐式记忆长期状态，规则也不会被生成误差破坏。同时，为了让玩家能自然创建和修改玩法，还需要一个多模态编码智能体，把自然语言转成游戏代码与动态字幕。

3. 核心贡献（约300字）

论文提出 Matrix-Game V4 路线图：用可执行游戏支架把视频生成模型包裹起来，分离游戏执行与视觉生成。基于该路线图实现 Matrix-Game 4.0：游戏引擎维护持久世界状态并执行规则；多模态编码智能体把玩家想法变成游戏代码和动态字幕；自回归视频渲染模型把引擎输出的低多边形代理渲染成高保真画面。

论文构建了 UE5 像素级对齐的低多边形/高保真视频对，以及随引擎状态变化的动态字幕数据管道；提出了“监督微调 + 因果少步蒸馏”的训练方案，把双向视频模型变成每 chunk 一到两步的因果生成器；并做了面向实时推理的系统级优化。在 RTX 5090 上实现 480p、60 FPS 游戏，键到显示延迟 112 ms，单步生成吞吐 83 FPS，峰值显存 18.2 GiB；RTX 5080 和 RTX 5070 Ti 上分别达到约 67 FPS 和 58 FPS。验证实验显示 40 秒 rollout 中布局、相机和物体运动保持稳定，并展示了智能体为射击/驾驶游戏添加健康弹药、检查点计时赛、追击模式等玩法。论文同时开源代码、模型权重复现和低多边形游戏资产。

4. 推理阶段整体流程与基模（约400字）

推理时的基模包括：Wan2.2 系 5B 参数的 DiT 视频渲染模型，作为神经渲染器；umT5-xxl 作为动态字幕文本编码器；TAEHV 作为轻量视频解码器。游戏引擎与多模态编码智能体是外部状态执行器和指令/字幕生成器。

整体流程可以理解为：引擎先根据玩家输入更新世界状态，并把当前场景画成低多边形草图；智能体或规则模板把引擎状态翻译成文字；渲染模型基于草图、文字和历史画面生成高保真帧。

图 2：Matrix-Game V4 路线图：多模态编码智能体与游戏引擎共同构成视频生成模型的支撑框架。玩家将想法和请求发送给智能体，将动作发送给引擎（1）。智能体编写世界，将想法变成供引擎使用的游戏代码和场景，并翻译世界，将引擎报告的状态和事件转成文本描述。引擎在代码中维护世界状态和规则（2），并以场景的结构化渲染形式发送控制信号（3）。视频生成模型根据文本描述、其历史帧和结构化渲染实时渲染帧（4）。生成的帧作为视觉反馈返回给玩家（5）。

  1. 玩家输入（键盘/鼠标动作和自然语言想法/修改请求）→ 系统拆分：动作直接进入游戏引擎，语言请求进入多模态编码智能体 → 引擎得到玩家操作，智能体得到创建/修改意图。
  2. 智能体把意图转换为可执行游戏代码、场景定义和动态字幕模板 → 交给游戏引擎注册/更新规则；引擎随后把当前状态/事件回传给智能体用于字幕更新 → 引擎拥有更新后的世界规则，字幕生成条件就绪。
  3. 引擎按固定步长更新世界状态，执行碰撞、生命值、目标等规则，并渲染低多边形代理（包含空间布局、对象位姿和运动）→ 输出当前帧代理和结构化控制信号 → 交给渲染模型作为空间约束。
  4. 引擎同时提供当前可见对象 ID 和事件，智能体/规则模板生成动态字幕（哪些对象、什么状态、发生什么变化）；系统检索与当前相机位姿最接近的空间记忆帧和首帧作为参考 → 输出语义条件与历史参考 → 交给渲染模型。
  5. 渲染模型将低多边形代理、动态字幕编码、参考帧和 KV 缓存中的最近 20 个 chunk 作为上下文，对当前 chunk（1 个潜变量帧 = 4 个视频帧）做一次或两次流更新，再由 TAEHV 解码 → 输出 4 帧高保真画面 → 交给显示端。
  6. 显示端把画面呈现给玩家；已生成 chunk 的键值写入环形 KV 缓存，用于下一 chunk 的自回归条件 → 玩家看到画面后产生新的输入，回到步骤 1 形成闭环。

5. 核心方法（约600字）

原论文没有名为 Method 的独立章节；方法正文对应第 2 至第 5 节，以下按原编号与英文标题展开。

2 Roadmap（路线图）

整体路线是让游戏引擎、多模态编码智能体、视频生成模型三者各司其职，把视频模型放入外部“游戏支架”中，而不是让它独自承担世界模拟。

2.1 Game Engine: The World’s “Referee”（游戏引擎：世界的“裁判”）

引擎用简化几何表示道路、建筑、角色和交互物，把碰撞、生命值、任务进度等规则显式写在代码里。它输出低多边形代理作为“场景草图”，给视频模型提供空间布局、物体运动和相机约束；即使物体离开视野，引擎仍按规则维护其状态。

2.2 Multimodal Coding Agent: The World’s “Scriptwriter” and “Translator”（多模态编码智能体：世界的“编剧”与“翻译”）

智能体双向工作：下游把引擎状态和事件翻译成文本描述，即动态字幕；上游把玩家想法实现为游戏代码和场景定义，交给引擎注册。例如设计“怪物从四面八方涌来”时，需要定义生成位置、移动攻击方式和胜负条件，而不只是增加怪物视觉。

2.3 Video Generation Model: The World’s “Painter”（视频生成模型：世界的“画家”）

视频模型以低多边形代理、动态字幕和历史帧为条件，通过因果自回归逐块生成高保真帧。少步蒸馏和推理优化使实时生成成为可能，同时不负责记忆世界状态或执行规则。

3 Data（数据）

3.1 Paired Low-Poly and High-Fidelity Capture（配对低多边形与高保真捕获）

在 Unreal Engine 5 中用同一相机和帧索引记录低多边形结构渲染与高保真 RGB 帧，得到像素级对齐的代理-真值视频对；同时记录对象 ID、可见性、事件等元数据。数据覆盖中世纪城堡、古埃及沙漠、沙漠峡谷空战、城市驾驶四类场景，共 114,334 个片段、约 1,712 小时。低多边形表示去掉材质、纹理和光照，只保留空间布局与运动轨迹，从而为视频模型提供确定性的结构监督。

图 3：UE5 配对训练数据。(a) 每个片段在 Unreal Engine 5 中以相同相机和帧索引捕获两次：一次作为保持场景布局和运动的低多边形结构渲染（BBox），一次作为高保真 RGB 帧。(b) 对于每个 81 帧片段，将相机位姿、动作、可见对象、事件和环境的帧对齐 CSV 记录转换为提示词：在描述表中查找可见对象 ID，组合空间和时间线索，模板生成片段提示词。

3.2 Dynamic Captions（动态字幕）

固定文本无法跟随玩家操作改变，因此系统根据引擎报告的可见对象 ID、状态和事件，用规则模板为每一帧生成动态字幕。字幕提供“场景里有什么、处于什么状态”，低多边形代理提供“物体在哪里、如何运动”，二者共同约束视频模型。该过程不需要视觉语言模型，而是基于对象 ID 到语义描述的查找表。

图 4：动态字幕跟随引擎状态。上：一个 CitySample 驾驶片段的低多边形代理帧；编号标记是引擎为该帧报告的可见对象，每个标记通过其实例 ID 关联到语义描述。下：基于规则的模板为同一帧生成的字幕，不使用任何视觉语言模型。橙色文本来自对象状态和事件，蓝色文本来自对象位置和距离。随着汽车移动，停放的车辆从描述中消失，行人由站立变为接近，新可见对象在“Changes”下被提示。

4 Rendering Model（渲染模型）

4.1 Architecture（架构）

渲染模型由 Wan2.2-Fun-5B-Control 改造为视频到视频模型。每个 chunk 对应 1 个潜变量帧（4 个视频帧）。输入包括噪声潜变量（48 通道）、TAEHV 编码的低多边形代理（48 通道）和 52 个零通道，拼接后 patchify 为每潜帧 405 个 token。30 个因果 DiT 块在 KV 缓存上做自注意力，并对动态字幕的缓存 KV 做交叉注意力；输出头预测速度，经 1 或 2 步流更新后由 TAEHV 解码。KV 缓存保存空间记忆帧、参考帧和最近 20 个 chunk；完成的 chunk 会在 t=0 且无控制输入时重跑一次，把其键值写入缓存，供后续 chunk 使用。

图 5：渲染模型架构。一个 chunk 的带噪潜变量（一个潜变量帧、四个视频帧）与由 TAEHV 编码的低多边形代理拼接为 148 个通道，并在 480×864 下被分块为每个潜变量帧 405 个 token。30 个因果 DiT 块在保存空间记忆帧、参考帧和最近 20 个 chunk 的 KV 缓存上执行自注意力，对动态字幕的缓存文本键和值执行交叉注意力，并经过前馈网络；每个块通过 AdaLN 由时间步调制。输出头预测一个速度，一次或两次 flow 更新产生干净潜变量，TAEHV 解码四帧。完成后的 chunk 在 t=0 且无控制输入的情况下重新运行，以将其键和值写入缓存。

4.2 Supervised Fine-Tuning（监督微调）

在 704×1280 的 81 帧窗口上微调，条件包括低多边形代理、动态字幕、首帧和最多 3 个空间记忆帧。空间记忆帧取自窗口前至少 40 帧、且视角与当前窗口重叠的干净帧。首帧、提示词、代理分别以 0.3、0.2、0.2 的概率随机丢弃，以支持无首帧生成和无分类器引导（CFG）。训练使用 64 张 GPU、全局 batch 64、AdamW、学习率 \(10^{-5}\)，共 4000 步。

4.3 Causal Few-Step Distillation（因果少步蒸馏）

为了实时生成，按 Causal Forcing++ 把双向模型变成因果自回归少步生成器，分三阶段：

  1. Teacher-forced autoregressive diffusion：让每个潜变量帧拥有自己的噪声水平，且只注意它之前的干净帧，训练 20,000 步得到因果教师。
  2. Causal consistency distillation：在 48 级噪声网格上，教师从高噪声到低噪声做一步 Euler；在线学生匹配 EMA 学生在低噪声层的预测。5,000 步后，EMA 学生可以 4 步生成一个 chunk。
  3. Distribution matching：学生用自己的自回归 rollout 训练；真实得分来自冻结双向模型，假得分网络在线更新。最终学生每个 chunk 只用 2 步、首帧用 4 步。最新配方还使用首帧 + 最近 20 帧的滚动缓存，每 20 帧段检索至多 3 个空间记忆帧，并混合 TAEHV 与 Wan-VAE 编码的代理控制。

5 Real-Time Inference（实时推理）

推理优化按表 2 累积应用：CUDA Graph 消除 CPU 启动开销；TAEHV 替换完整 Wan VAE；RoPE、归一化、FP8 量化写成 Triton 融合 kernel；缓存文本 KV；使用 FP8 权重；加入 1 步蒸馏；异步 I/O 管线；环形 KV 缓存避免移动整个窗口；split-KV FlashAttention 并行计算并合并注意力。最终在 RTX 5090 上把生成吞吐从 4.5 FPS 提升到 83.4 FPS，键到显示延迟从 1110 ms 降到 112 ms。单步生成约 83 FPS，两步约 57 FPS，峰值显存约 18.2 GiB；RTX 5080 和 RTX 5070 Ti 在固定提示下单步约 67 / 58 FPS。

图 6：推理优化总览。(a) RTX 5090 上逐 block 的 GPU 时间，按内核类别分解。(b) 解码被移到 clean-KV 更新之前，因此帧更早输出。(c) 环形缓存不是每一步都移动整个 KV 窗口，而是将新帧写入最旧的槽位。(d) 自注意力被拆分为七个窗口范围，其量化的键和值被缓存；部分输出通过 log-sum-exp 合并。

6. 局限性和展望（约300字）

论文明确展示的系统目前面向 UE5 中的四类场景（城堡、沙漠、空战、城市），玩法以射击和驾驶为主，且每个游戏单独训练一个渲染模型；扩展到新的游戏类型需要新的配对数据与训练成本。输出分辨率为 480p，作者计划进一步提高视觉保真度，并加入面向更高分辨率的细化阶段。推理成本仍然较高：当前结果依赖 RTX 5090、RTX 5080、RTX 5070 Ti 等 16 GB 以上显存的消费级 GPU，更低端设备上难以达到 60 FPS；作者明确计划降低推理成本和硬件要求，并发布 Steam 技术预览。多人共享世界与一致视角只作为路线图方向提出，尚未给出实现结果。

可以谨慎推断的限制包括：动态字幕依赖对象 ID 到语义描述的规则表和模板，面对长尾或全新对象时可能需要额外人工设计描述；低多边形代理必须由引擎生成，如果场景没有现成的轻量几何表示，系统难以直接套用；用自然语言生成复杂玩法时，智能体需要写出可编译的游戏代码，长尾编辑请求的稳定性尚未被充分验证。未来方向还包括更精确的视觉控制、更多游戏类型与场景，以及多人渲染一致性。
