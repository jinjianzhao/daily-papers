GameWAM: A World Action Model for Video Games

一句话主题： 视频游戏中的世界建模与动作生成

领域标签： 游戏智能体 / 世界动作模型 / 视觉动作生成

快速理解

背景与任务： 视频游戏需要同时理解快速变化的画面、世界状态和多样的原生控制方式。

核心工作： 作者提出GameWAM，联合预测未来画面与可执行键鼠动作，并支持长时闭环游戏控制。

中文摘要

现代视频游戏结合了第一人称感知、快速视觉变化、持久的世界状态以及异构的原生控制。现有游戏智能体将视觉和任务上下文直接映射为动作，但缺乏显式的世界动力学建模；而交互式游戏世界模型会根据给定动作预测视觉未来，但不能作为任务策略。世界-动作模型（World-Action Models, WAMs）统一了这些目标，但在视频游戏的动态性和开放式交互条件下仍基本未被探索。我们提出 GameWAM，据我们所知，这是首个用于原生闭环游戏玩法和 GUI 控制的 WAM。GameWAM 通过具有块因果条件（block-causal conditioning）和流匹配（flow matching）的并行视觉与动作生成过程，联合生成未来视觉观测和可执行的键盘-鼠标轨迹。为支持联合世界-动作学习，我们构建了同步的游戏玩法和 GUI 轨迹。为处理异构的原生控制，GameWAM 在每个动作步骤预测游戏玩法/GUI 模式，并使用模式特定的预测分布和连续动作归一化来生成动作。对于长时程交互，块循环控制（block-cycle control）会预测超出已提交时域的内容，仅执行一小段动作前缀，并从新的观测结果重新规划；与此同时，细粒度的循环内上下文和层次化的跨循环历史保持时间连续性。实验表明，在与对比智能体相比执行更少原生动作的情况下，GameWAM 取得了具有竞争力的任务成功率。我们进一步揭示了低频动作源印记效应（Low-Frequency Action Source Imprinting, LASI）：在固定条件下，所采样动作源的低频分量会系统性地引导生成的粗粒度相机运动，揭示了生成式控制中的一种源敏感性失效模式。项目页面见 https://yunncheng.github.io/GameWAM/。

详细分析

下面按“对低年级博士生讲论文”的方式来讲 GameWAM。你已经熟悉 Transformer，所以我会重点解释：它到底在建模什么、为什么普通 agent 不够、它的关键机制如何落地、实验结论到底证明了什么。

1. 任务输入、输出、功能和边界

任务是什么

这篇论文研究的是：在视频游戏里，让模型既会“预测未来会看到什么”，又会“直接生成可执行的键鼠动作”。 这里的“可执行”指的是原生控制，不是抽象动作标签，而是：

  • 键盘按键：W/A/S/D、跳跃、攻击、快捷键等
  • 鼠标动作：视角旋转、光标移动、点击、滚轮等
  • 还包括不同模式下的控制语义：gameplay 模式和 GUI 模式

输入是什么

GameWAM 每次决策时的输入主要包括：

  1. 当前视觉观测

也就是游戏画面，通常是第一人称视角，变化快、信息密集。

  1. 任务指令 / 文本目标

例如“挖白床”“收集黑曜石”“做一个 dispenser”。

  1. 历史状态

包括最近几步执行过的画面、跨 cycle 的长期记忆。

  1. 可选的 proprioceptive / state 信息

比如游戏内部状态、位置、GUI 状态等。

输出是什么

它同时输出两类东西：

  1. 未来视觉观测

即接下来若干步可能看到的画面表示。

  1. 未来 native action trajectory

即接下来若干步要执行的键鼠动作序列。

换句话说，它不是只输出“下一步动作”，而是输出一个短期计划： “未来会怎样 + 我该怎么做”。

功能边界是什么

它的目标边界是：

  • 面向闭环游戏控制：执行动作后立刻观察新画面，再重规划
  • 面向原生键鼠控制：不是高层语义动作，不是离散宏动作
  • 同时覆盖 gameplay 和 GUI：例如打怪、探索、合成、界面操作
  • 只在模拟游戏环境和 GUI 环境中验证：不是物理机器人，也不是任意真实软件自动化

也就是说，它解决的是“游戏里的原生闭环控制”，不是泛化到所有交互软件的通用系统。

2. 论文要解决的问题，以及问题为什么会出现

论文要解决的核心问题

作者认为，现有方法分成两类，但都不完整：

A. 游戏 agent / VLA policy

这类模型直接从“当前画面 + 指令”映射到动作。 问题是：它会做动作，但不显式预测动作会带来什么视觉后果。

B. interactive world model

这类模型会根据动作预测未来画面。 问题是：它能想象世界怎么变，但它不是任务 policy，不会自己选动作。

所以作者提出：

能不能做一个统一模型，既负责“想象未来”，又负责“生成动作”？

这就是 World–Action Model (WAM)。

这些问题为什么在游戏里更严重

游戏环境比很多机器人任务更难，原因很具体：

1. 第一人称视觉变化快

玩家一转头，画面就完全变了；敌人、物体、GUI 状态变化都很快。

2. 原生控制异构

同一套键鼠通道在不同场景语义不同：

  • 在 gameplay 中，鼠标可能表示视角转动
  • 在 GUI 中，鼠标可能表示光标移动和点击

如果把它们混成一个分布学，容易把统计量混乱掉。

3. 动作需要精细时间结构

例如连续转视角 + 离散按键 + 鼠标点击要协同发生。 如果只做粗粒度动作抽象，可能失去节奏和幅度信息。

4. 闭环交互要求频繁反馈

如果一次计划太长，模型会在旧观测上“想太远”，偏离实际环境； 如果计划太短，又会缺少前瞻性。

5. 长期记忆问题

游戏里很多状态是持久的，比如：

  • 位置
  • 物品栏
  • 血量
  • 已经打开/关闭的 GUI
  • 之前做过的规划

如果只看最近几帧，容易丢失关键上下文。

3. 核心 insight 与贡献

核心 insight

作者的核心想法可以概括成一句话：

把“预测世界”和“生成动作”放在同一个闭环生成框架里，让未来视觉监督反过来约束动作生成。

这比“只做动作”多了一个约束： 动作不能只看起来像专家动作，还要和未来观测一致。

主要贡献

可以分成四点：

  1. 提出 GameWAM
    • 第一个面向 native closed-loop gameplay 和 GUI control 的 WAM
    • 统一生成未来视觉和键鼠动作
  1. 构造同步的训练数据
    • 把 gameplay 轨迹、事件中心轨迹、脚本 GUI 轨迹统一到同一时间线上
  1. 提出适配游戏的控制机制
    • mode router 区分 gameplay / GUI
    • block-cycle 控制做“预测长、执行短”
    • 分层历史保留长期上下文
  1. 发现 LASI 现象
    • 采样源的低频成分会稳定地影响生成出的粗粒度摄像头运动
    • 这是一种生成控制中的 source-sensitivity 失败模式

4. 使用的基模，以及从输入到输出的整体流程

基模是什么

GameWAM 的主体是两个并行的 Transformer 生成器：

  • Video DiT
  • Action DiT

它们不是普通分类器，而是用 flow matching 做生成。 你可以把它理解为：从随机噪声出发，在 Transformer 预测的“速度场”引导下，逐步变成目标视频 token / 动作 token。

整体流程

先看总体架构。

Figure 1：GameWAM 概览。GameWAM 联合建模未来视觉观测和原生动作，用于 closed-loop gameplay 和 GUI control。

Figure 2：GameWAM 的训练与推理架构。并行 Video 和 Action DiTs 联合建模未来观测和原生动作，并采用 block-causal 交互以及 gameplay/GUI 特定的动作生成。

训练时怎么走

训练时，模型拿到：

  • 历史观测
  • 指令
  • 当前 block 的 clean prefix
  • 被加噪的未来视频和动作

然后：

  1. Video DiT 预测未来视觉的 flow
  2. Action DiT 预测未来动作的 flow
  3. 两者共享同一个 causally available prefix
  4. 用 flow matching loss 训练

注意：它不是简单地做监督学习预测下一个动作，而是联合建模整段短期未来。

推理时怎么走

推理时：

  1. 从噪声初始化动作和视频变量
  2. 逐步积分 flow ODE，生成未来计划
  3. 只执行计划前面一小段动作
  4. 观察新画面
  5. 重新规划

这就是闭环控制。

5. 每个关键机制为什么需要、怎么做、得到什么

5.1 Block-causal 建模：为什么需要？

为什么需要

如果直接让“未来视频 token”和“未来动作 token”互相看见彼此，会有信息泄漏问题。 训练时模型可能偷看不该看的未来变量，推理时却没有这些信息。

怎么做

作者定义了 block-causal visibility：

  • 当前 block 可见的只有 clean causal prefix
  • 未来的噪声视频 token 和动作 token 不能跨模态互相条件化
  • 训练时用 teacher forcing
  • rollout 时只保留真实执行过的部分

这类设计在图上更直观。

Figure 6：默认的 modality-decoupled world–action 形式下的 block-causal 可见性。训练视图（左）和 autoregressive rollout 视图（右）展示了三个重叠的计划。视觉和动作预测接收相同的干净 causal prefix，而同时被污染的未来视觉和动作 token 不用于跨模态条件。训练时已完成的 blocks 使用 teacher forcing；在 rollout 时，只有通过已提交执行到达的观测会进入干净前缀。已计划但未执行的后缀会在下一次决策前丢弃。彩色单元格表示可见条目，灰色单元格表示被 mask，绿色单元格表示保留的干净上下文，斜线单元格表示已预测但未执行的变量。

得到什么

  • 训练和推理的因果结构一致
  • 避免未来信息泄漏
  • 保证动作生成是“基于真实可得上下文”的

5.2 为什么要同时预测未来视频和动作？

为什么需要

只学动作，模型不知道动作会带来什么后果； 只学视频，模型不会选动作。

联合学习的好处是：

  • 视频预测给动作提供“世界后果”监督
  • 动作预测给视频生成提供任务相关性
  • 两者共享上下文，彼此约束

怎么做

训练目标里有：

  • 视频 flow loss
  • 动作 flow loss
  • mode 分类 loss
  • history prediction loss

其中动作和视频都是通过 flow matching 学的。

得到什么

模型不只是模仿动作模式，还能学到“某个动作序列会对应怎样的视觉演化”。

5.3 Mode router：为什么要区分 gameplay 和 GUI？

为什么需要

gameplay 和 GUI 都用键鼠，但统计分布不同：

  • gameplay：常见的是移动、转视角、攻击、跳跃
  • GUI：常见的是光标移动、点击、拖拽、快捷键

如果混成单一分布，模型会把两种行为的控制尺度和语义混淆。

怎么做

对每个 action step，模型先预测一个 mode：

  • 0 = gameplay
  • 1 = GUI

然后用对应的动作分支去生成该步动作：

  • U_game
  • U_gui

连续动作坐标还会按各自统计量做不同 normalization。

得到什么

  • 同一物理键鼠通道能兼容两种任务
  • 减少“GUI 光标统计”和“游戏视角统计”混淆
  • 实验里这个设计优于统一动作分布

5.4 Block-cycle control：为什么要“预测长、执行短”？

为什么需要

如果每次都把很长的动作计划一次性执行完：

  • 反馈太慢
  • 一旦中途偏离，就没法及时修正
  • 游戏里目标和视觉状态变化很快

如果每次只预测很短：

  • 没有前瞻性
  • 容易陷入局部抖动

所以作者让模型：

  • 预测长度是 P
  • 真正执行长度是 E
  • 且 E < P

也就是： 预测更远，执行更短，再根据新观测重规划。

怎么做

每个计划块生成 P 步动作，但只执行前 E 步。 然后环境推进，得到新的观测，再用新的上下文继续规划。

训练时也用同样的块结构，但通过 overlapping supervision 来学习。

Figure 3：Block–cycle 控制与分层历史。GameWAM 在只执行短前缀的同时预测超过已提交时域的内容，并结合瞬时的 cycle-local K/V cache 与持久的跨 cycle 视觉历史。

得到什么

  • 既有前瞻性，又保留频繁反馈
  • 更适合移动目标、快速战斗、复杂 GUI 操作
  • 这是论文里很关键的系统设计

5.5 分层历史：为什么要 cycle-local cache + cross-cycle memory？

为什么需要

只靠当前 block 的 cache 会有两个问题：

  1. 短期上下文不够
  2. 跨 block 的长期状态会丢失

游戏里很多信息不能只记几帧，比如：

  • 你已经走到哪
  • 某个 GUI 已经打开
  • 之前那个目标块在哪里

怎么做

作者把历史分成两层：

  1. cycle-local K/V cache
    • 保留当前 cycle 内的细粒度上下文
    • 到 cycle 边界会重置
  1. persistent cross-cycle history
    • 最近视觉片段先经 VAE + Conv3D 压缩
    • 用 FIFO 缓冲保留最近片段
    • 再用 attention pooling 更新 long-term memory slots

这相当于：

  • 短期细节放在 cache 里
  • 长期摘要放在 memory 里

得到什么

  • 保持细粒度控制连续性
  • 同时保留跨 cycle 的任务上下文
  • 对 GUI 和 combat 更有帮助

5.6 同步轨迹构造：为什么需要专门做数据处理？

为什么需要

如果只拿普通游戏录像，里面可能没有：

  • 对齐的动作序列
  • 明确的 mode 标签
  • 适合 WAM 的同步观测-动作窗口

而 WAM 需要每个时间点都知道：

  • 观测是什么
  • 动作是什么
  • 是 gameplay 还是 GUI
  • 哪些事件段更重要

怎么做

作者构造三类数据流：

  1. regular VPT trajectories
    • 宽覆盖、长上下文
  1. Event-Anchored VPT
    • 围绕交互事件密集采样
    • 强化目标相关片段
  1. scripted GUI trajectories
    • 扩充界面交互数据

所有数据都标准化到共同时间线。

Figure 8：构建可用于 WAM 的游戏轨迹。VPT 录制被标准化为 regular 和 Event-Anchored datasets；事件分支检测交互事件、提取锚定窗口、过滤时间上冗余的候选项，并对不同事件类型执行 max–min fair allocation。基于 MineStudio 的脚本化 GUI 轨迹扩展了界面交互覆盖范围。所有流都共享相同的原生动作空间和轨迹表示，用于联合 world–action 训练。

得到什么

  • 训练样本与闭环控制目标一致
  • 事件附近的关键行为被更多看到
  • 提升动作学习和视觉监督的质量

5.7 为什么要用 flow matching？

为什么需要

flow matching 适合连续生成问题，特别是：

  • 连续 camera motion
  • 混合连续 + 离散的 native action
  • 长序列生成

相比直接分类下一个动作，它更适合生成“轨迹”而不是单点标签。

怎么做

对视频和动作都定义噪声变量 X_σ，学习速度场 U = ε - X_0。 推理时从高斯噪声出发，积分到数据分布。

得到什么

  • 可以统一处理动作轨迹生成
  • 连续摄像头控制更自然
  • 与 transformer backbone 配合良好

6. 主结果、消融结果、可视化结论及证据边界

6.1 主结果：MCU 上的表现

论文在 Minecraft Universe（MCU）上评估了 800+ 任务，分三类：

  • Embodied tasks
  • GUI tasks
  • Combat tasks

结论是：

  • GameWAM 的平均成功率最好
  • 而且执行的 native actions 更少

具体看表中结果，GameWAM 的平均指标大致是：

  • Mini：50.7
  • Full：46.6

并且在三个任务类别里，平均成功率和动作效率都较强。 尤其显著的是：它在获得成功的同时，所需步数明显更少。 例如它的步数大约是：

  • Embodied: 138
  • GUI: 155
  • Combat: 203

相比很多基线的 290–400+ 步，少了很多。

这说明它不只是“会做”，而是更省动作地完成任务。

6.2 主结果：ViZDoom 上的表现

在 ViZDoom 四张地图上，GameWAM 也表现出：

  • 稳定提升
  • 在多场景下接近或达到领先
  • 对快速视觉变化和连续战斗有较强适应性

这说明它不是只在 Minecraft 这类任务上有效，也能适应更快节奏的第一人称战斗环境。

6.3 几个典型可视化结果

这些图主要是 qualitative evidence：它们展示“模型到底会不会闭环做事”。

例子 1：先探索，再找到目标

在“Mine the white bed”里，目标一开始不可见，模型先探索附近，再进入结构体，获得目标视野并完成任务。

6.4 消融结果说明了什么

表 2 里最重要的消融结论是：

1. 去掉未来视频监督，掉得最多

这说明：

  • 只学动作不够
  • 未来视觉监督确实在帮动作学习

这是作者最核心的实证支持。

2. 更粗的 temporal sampling 会明显变差

说明：

  • 游戏里很多关键变化发生得很快
  • 采样太粗会漏掉重要转折

3. 去掉 event-anchored sampling 会变差

说明：

  • 围绕关键交互事件密集采样，确实更有效

4. 统一动作分布不如 mode-specific 分布

说明：

  • gameplay 和 GUI 的动作统计不同
  • 合并分布会损失表达精度

5. P = E 变差

说明：

  • 只预测到刚好执行的长度不够
  • 预测比执行更长有助于规划和纠错

6. 去掉跨 cycle history 会有一定下降

但影响没有前几项大，而且有任务差异：

  • GUI 和 combat 更依赖它
  • embodied task 甚至有一点点上升

这说明长期历史有用，但不是所有任务都同等依赖。

6.5 LASI 的可视化/实验结论

作者还发现一个很重要的现象：Low-Frequency Action Source Imprinting (LASI)。

现象是什么

在固定条件下，如果重复使用同一个采样源，某些低频成分会让生成的摄像头动作出现稳定偏向，比如：

  • 持续朝某个方向旋转
  • 重复原地转圈

证据是什么

作者做了三种控制实验：

  1. 固定条件下看 source 和输出的相关性
    • 低频部分，尤其 yaw 的 DCT0，相关很强
  1. 替换 source 的低频部分
    • 输出也跟着 donor 的低频特征走
  1. 把 source 的低频部分置零
    • 相关输出方差大幅下降

这说明什么

这不是单纯“采样有随机性”，而是：

  • 采样源的低频结构会系统性影响粗粒度 camera motion

证据边界

这里要注意边界：

  • 这是在固定条件下做的受控实验
  • 说明的是 GameWAM 的生成控制里存在 source sensitivity 问题
  • 不能直接外推成“所有生成模型都会这样”
  • 也不能说这是环境问题，而是模型生成路径对采样源敏感

作者的实际应对是： 在闭环 rollout 里不复用同一个 source，而是每次重新采样，减少这种偏置累积。

7. 局限性和最终判断

局限性

1. 仍然是游戏/模拟环境

它验证的是 Minecraft 和 ViZDoom，尽管很有代表性，但还不是现实世界软件或物理系统。

2. 依赖同步轨迹和 mode 标注

这个方法很吃数据工程：

  • 要对齐动作和观测
  • 要区分 gameplay / GUI
  • 要构造 event-anchored 样本

这使得迁移到别的环境时，数据准备成本不低。

3. 系统复杂度高

它不是一个简单 policy，而是把：

  • 双 DiT
  • flow matching
  • mode router
  • block-cycle control
  • hierarchical history
  • 轨迹构造

全部组合在一起。 这对复现和部署都增加复杂性。

4. LASI 显示生成控制仍有脆弱点

即使整体性能好，生成源偏置仍可能造成闭环积累误差。 这说明“会生成动作”不等于“控制就完全稳定”。

最终判断

如果只看这篇论文本身，我会把它判断为：

  • 问题定义清楚
  • 系统设计扎实
  • 实验结果支持主要主张
  • 最有价值的贡献是把 WAM 真正推进到原生闭环游戏控制场景
  • LASI 这个失败模式的发现也很有研究价值

它的核心意义不是提出一个单点 trick，而是证明：

在游戏这种高频、异构、强闭环环境里，把世界预测和动作生成统一起来，确实比只做 policy 更有优势。
